# V1.7 — Duplicate-position expansion in tile layout

**Date:** 2026-04-30
**Author:** Gabriel Declercq (with Claude)
**Status:** in progress
**Branch:** Version-1.7

## Goal

Handle ND2 acquisitions where multiple multipoints (M indices) share
the same physical (X, Y) — i.e., the file revisits the same positions
across "scan cycles" rather than encoding each visit as an additional
T point.

## Concrete case (the user's file)

`Well2_Channelp53-GFP,ERK-mRuby2,H2B-iRFP670,TD_Seq0000.nd2`:

- `dim_order = TPZCYX`, sizes `T=80, P=68, Z=3, C=4, Y=1024, X=1024`.
- Pixel size 0.8613 µm/px → tile size 882 × 882 µm.
- Stage XY: only **2 unique X values** (-29032.6, -26386.8 µm) and
  **17 unique Y values**, but **4 unique M indices map to each
  physical cell** (M=0, 17, 34, 51 are all at the same (x, y); ditto
  for every other physical position).
- Net: 68 multipoints across 17 unique physical cells × 4 visits.
- The scan is a **zigzag/checkerboard** — each phys row uses only
  one of the two phys cols (alternating).

V1.6 correctly clustered the data into 2 cols × 17 rows = 34 phys
cells (17 of which are populated by the zigzag). But it placed all
4 M's at the same cell on top of each other, so the layout widget
piled labels like "M=0 / M=17 / M=34 / M=51" inside one rectangle.

## Approach

After clustering and assigning each M to a `(col_idx, row_idx)`:

1. Build `assignments: List[(m, col_idx, row_idx)]`.
2. Count occupants per cell: `cell_counts[(col_idx, row_idx)]`.
3. `max_dup = max(cell_counts.values())`.
4. **If `max_dup == 1`** — every M has its own cell → use V1.6 layout
   unchanged.
5. **If `max_dup > 1`** — expand each phys col into `max_dup`
   sub-cols. Within each cell the M's are sorted by index; the i-th
   M (0-based) lands at sub-col `i`. Empty sub-cells (cells with
   fewer than `max_dup` occupants, or unvisited cells in a
   checkerboard) appear as background.

Final canvas dimensions:

```
n_cols_visual = n_phys_cols × max_dup
n_rows_visual = n_phys_rows
canvas_w      = n_cols_visual × tile_w
canvas_h      = n_rows_visual × tile_h
offset(m)     = (row_idx[m] × tile_h,
                 (col_idx[m] × max_dup + sub_idx[m]) × tile_w)
```

For the user's file: `2 × 4 = 8` visual cols × `17` rows = 136 cells,
68 populated. The empty cells visualize the zigzag — half of each row
is empty because the checkerboard skips that physical column on that
row. That's actually informative.

### Diagnostic

`compute_tile_layout` adds a `n_visits_per_cell` field on
`StitchLayout`. The Import metadata table reports it as a richer
"Tile source" string, e.g.:

- `"68 of 68 from stage XY"` — every M unique (V1.6 behaviour).
- `"68 multipoints → 17 unique cells × 4 visits → 8 × 17 layout"` —
  the user's case.
- `"grid fallback (no stage XY metadata)"` — V1.4 behaviour.

## Key Decisions

1. **Horizontal expansion only.** Sorting M's left-to-right inside a
   cell preserves a "M index increases as you scan right" reading
   that matches the temporal order of acquisition cycles. A 2D
   sub-grid would obscure that.
2. **Sort sub-positions by M index.** Doesn't depend on fragile
   per-acquisition conventions; whatever order the file's M axis
   uses is reflected directly.
3. **Show empty cells as ghost outlines.** Surfaces the scan pattern
   (checkerboard, zigzag, sparse acquisition) visually rather than
   hiding it.
4. **Same expanded layout drives stitch export.** A 4-cycle
   contact sheet is useful for QC even if not a "true" stitched
   field. Cycle blending stays out of scope.

## Validation

- Synthetic test mirroring the user's file:
  - 17 phys-row Y values 882 µm apart.
  - Each row visited 4 times in 4 cycles.
  - Cycles alternate between 2 phys cols (zigzag).
  - Total 68 multipoints; small ±0.1 µm jitter on each X.
- Expected V1.7 output: `8 cols × 17 rows`, 68 unique offsets
  (one per M), 4 visits per cell.
- All other tests (regular grid, no duplicates) keep V1.6 behaviour.
