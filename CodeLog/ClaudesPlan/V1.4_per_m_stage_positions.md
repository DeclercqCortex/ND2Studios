# V1.4 — Per-M stage XY (tile layout bugfix)

**Date:** 2026-04-30
**Author:** Gabriel Declercq (with Claude)
**Status:** in progress
**Branch:** Version-1.4

## Goal

Fix the tile-layout overlap visible on a 68-tile dataset where multiple
M indices stack on the same visual position because the metadata
reader returns duplicate stage XY entries.

## Bug

`read_nd2_metadata_extended()` builds `stage_xy_um` by iterating

```python
n = out["n_timepoints"]
for t in range(n):
    fm = _safe(lambda i=t: f.frame_metadata(i))
```

`f.frame_metadata(i)` takes a **flat sequence index** (the i-th frame in
the entire file's flattened M × T × Z × C × Y × X stream), but the loop
treats `i` as if it were a multipoint index. For a typical Nikon
acquisition with dim order `PTZCYX`, the first `n_timepoints`
flat indices all live within `M=0`, walking through Z and C. The result:
`stage_xy_um` has many duplicate entries (often only 1–4 unique XYs),
and `compute_tile_layout()` faithfully draws every M-tile stacked on
top of those few unique positions.

Symptom captured in the user's screenshot: 68 tiles render at ~24
visual positions, with 2–3 tile-index labels piled inside each rect.

## Approach

### 1. Iterate per-M with a flat-index helper

Compute the flat sequence index for `(M=m, T=0, Z=0, C=0)` from the
file's `dim_order` and `sizes` (both already returned by the nd2
library), and call `frame_metadata` exactly once per M:

```python
def _flat_index(coords, dim_order, sizes):
    """Walk dim_order and accumulate a row-major flat index."""
    idx = 0
    for d in dim_order:
        if d in ("Y", "X"):
            continue          # spatial dims aren't part of the sequence
        idx = idx * sizes.get(d, 1) + int(coords.get(d, 0))
    return idx
```

The "sequence" axes are everything except Y and X. Most ND2 files use
one of `PTZCYX`, `TPZCYX`, `PTYX`, or `TYX`; the helper handles all of
them uniformly.

### 2. Split per-M and per-frame loops

Today both `stage_xy_um` and `frame_timestamps_s` come out of the same
`for t in range(n_timepoints)` loop. After the fix:

- `stage_xy_um`, `stage_z_um` ← length `n_multipoints`, one per M.
- `frame_timestamps_s` ← length `n_timepoints`, one per T (taken from
  the flat index for `(M=0, T=t, Z=0, C=0)`).

Movie export already pulls `frame_timestamps_s` per frame, so its
length needs to stay tied to T. No downstream change there.

### 3. Defensive fallbacks

- If `f.frame_metadata` raises for *every* M, `stage_xy_um` stays
  empty and `compute_tile_layout` falls back to its grid path —
  same V1.3 behaviour, just gracefully now.
- If a *subset* of M reads fail, log to `print(...)` (we haven't wired
  up a logger yet) and skip those entries; the layout draws whatever
  positions came back.
- Add a `stage_layout_source` field to the metadata dict
  (`"stage_xy"`, `"partial"`, or `"missing"`) so the GUI can show what
  happened.

### 4. Surface it in the Import metadata table

Add a "Tile source" row to the metadata table on the Import page:

- `"68 from stage XY"` — happy path.
- `"24 of 68 from stage XY · grid fallback for the rest"` — partial.
- `"grid (no stage XY metadata)"` — missing.

Lets the user verify at a glance whether the layout came from the
acquisition or from the fallback.

## Key Decisions

1. **Compute the flat index by hand from `dim_order` + `sizes`.** Avoids
   relying on undocumented `f.frame_metadata` keyword overloads that
   vary by nd2 library version.
2. **One metadata fetch per M, not per frame.** Even on a 68 × 200 × 11
   × 2 file, that's 68 calls instead of ~300 000. Fast.
3. **Don't deduplicate by position.** Two M positions can legitimately
   share an XY (focus retakes); we trust what the file reports.
4. **Keep timestamps per-T.** They drive movie overlays and need their
   per-frame granularity. The fix just stops them being conflated with
   stage data.
