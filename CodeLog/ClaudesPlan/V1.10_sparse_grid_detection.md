# V1.10 — Sparse-grid detection (irregular ROI scans)

**Date:** 2026-04-30
**Author:** Gabriel Declercq (with Claude)
**Status:** in progress
**Branch:** Version-1.10

## Goal

V1.8 switches to serpentine when an ND2 has **revisits**
(`max_dup > 1`). It does *not* switch when an acquisition has **gaps**
— i.e. an irregular / ROI-shaped scan that visits only a subset of
cells in a regular grid.

Concrete case the user just showed: a stitched output where the
populated tiles form an irregular ROI shape inside a 12 × 7 grid:

```
row 0: · █ · █ · █ · █ · █ · █
row 1: █ · █ · █ · █ · █ · █ ·
row 2: █ · █ · █ · █ · █ · █ ·
row 3: · █ · █ · █ · █ · █ · ·
row 4: · █ · █ · █ · █ · █ · ·
row 5: · · · █ · █ · █ · · · ·
row 6: · · · · █ · █ · · · · ·
```

33 / 84 cells populated (~39 %). With V1.8 each M is at a unique
physical (col, row), `max_dup = 1`, so serpentine doesn't fire — the
TIFF stitch keeps every empty cell as black background. The user
wants those gaps gone.

## Approach

After V1.7's cell-counting step, compute:

```python
fill_ratio = len(cell_to_local_indices) / (n_phys_cols * n_phys_rows)
```

**Switch to serpentine when EITHER:**

- `max_dup > 1` (revisits — V1.8 trigger), **OR**
- `fill_ratio < 0.9` (NEW — irregular / sparse ROI scan).

`fill_ratio = 0.9` is the threshold. A genuine 4 × 17 mosaic with
67/68 = 98.5 % stays on the physical path. The user's 33/84 ≈ 39 %
takes serpentine. Tunable in one place.

The serpentine algorithm itself is unchanged from V1.8:

- `n_rows_hint = n_phys_rows`
- `n_cols = ceil(N / rows)`
- M=0 at top-left, even rows L→R, odd rows R→L

For the user's 33-tile file: `n_phys_rows = 7`, `n_cols = ceil(33/7) = 5`.
Result: 5 × 7 = 35 cells, 33 populated, 2 trailing empty in the last
row. Tight, no internal gaps, M-index ordered.

### Source-label refinement

Both triggers emit `source = "serpentine"`, but we add a
sub-classification on `StitchLayout` so the diagnostic in
`import_page.py` can explain *why*:

```python
@dataclass
class StitchLayout:
    ...
    serpentine_reason: str = ""   # "revisits" | "sparse" | "" (not serpentine)
```

The "Tile source" row reads (e.g.):

- Revisits: `"68 multipoints → 17 unique cells × 4 visits → serpentine 4 × 17 layout (M=0 top-left)"`
- Sparse: `"33 multipoints in an irregular ROI (39 % of 12 × 7 grid populated) → serpentine 5 × 7 layout (M=0 top-left)"`
- Dense: `"68 of 68 from stage XY"`

## Key Decisions

1. **0.9 threshold.** Conservative; favors "physical layout" for
   anything that could plausibly be a real mosaic with one or two
   missed positions.
2. **Reuse the V1.8 serpentine algorithm verbatim.** No new layout
   logic; just an additional trigger condition.
3. **Same serpentine drives navigation and stitch export.** What you
   see in the sidebar is what the TIFF stitch produces.
4. **`serpentine_reason` on the dataclass, not in the source label.**
   Keeps `source` a small enum for code logic; reasons are surfaced
   in the human-readable diagnostic only.

## Validation

Synthetic test reproducing the user's exact 33-tile populated
pattern (extracted from `Stitch_test.tif`):

- 33 stage XY positions placed at the populated cells of a 12 × 7
  grid.
- After V1.10: source = `"serpentine"`,
  `serpentine_reason = "sparse"`, layout = 5 × 7, 33 unique offsets.
- M=0 at top-left.

Regression: dense regular 4 × 17 mosaic still uses physical layout
(`source = "stage_xy"`).
