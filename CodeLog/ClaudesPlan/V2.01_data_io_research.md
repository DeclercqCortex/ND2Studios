**Connectivity-reshape (your "well-known method"):** the headline match is the **flat
points-array + connectivity-array family — VTK `vtkCellArray` / FEM element-connectivity, with
CSR as its pure-graph sibling** (coordinates stored *once*, geometry *walked* from a flat 1D
connectivity array). `grid_to_graph` is how you *build* it from pixels; half-edge upgrades it
for editable vector boundaries; RCM / space-filling reorders it for locality; im2col is a
transient neighborhood gather, **not** a store. Full routes table + best-match analysis in §B.

## The single highest-leverage decision (do this first)

**Settle the provider's atomic read granularity — whole-frame (~85 MB) vs sub-frame tile —
with ONE benchmark, before writing `provider.py`.** It resolves the A↔C contradiction and
cascades into every open fork (tile size, whether structure domains are tiled, memo-key shape,
whether Track/Label can be lazy at all):

- **Frame-atomic** (accept C's "85 MB fits one texture" reality): no ND2→Zarr transcode,
  "selective full-res ROI" collapses to trivial, tiling becomes a pure **5D / memo-key** concern,
  and much of A's substrate complexity evaporates.
- **Sub-frame-tiled**: ND2 *must* be transcoded to a tiled store, a tile size must be chosen, and
  halo / border-merge machinery becomes mandatory.

Benchmark a tiled `QGraphicsScene` (or `QRhiWidget`) reading whole 6554² frames + coarsen-in-RAM
against a sub-frame Zarr path on a real 5D stack — then commit. Do not design two contradictory
substrates around an unmeasured assumption.

## Correctness landmines the critic flags (design against these, don't just caveat them)

1. **Memo lookup key must be a cheap PROXY** (file id + offset + mtime + params), **not a
   content hash** — you cannot hash a plane's pixels without reading the 85 MB plane. Keep
   **recipe-hash** (cheap, pre-materialization, for lookup) and **output-fingerprint**
   (post-materialization, for cutoff/dedup) as **two distinct hashes** with distinct lifecycles.
2. **CoW + identity-based invalidation = silent stale-hit bug** — a layer mutated in place keeps
   its object identity but changes content; identity-keyed memo won't invalidate downstream.
3. **Track/Label ids vs lazy pull** — tile-local CCL + border-merge can't promise a stable label
   id until a region's every spanning tile is realized; this fights demand-driven *partial*
   evaluation for the Track/Label domains specifically.
4. **Lattice reductions don't tile trivially** — `coarsen=reduce` across z,y,x crossing tile
   borders needs a **tree-reduce / halo**; only `refine=broadcast` tiles for free.
5. **Hidden calibration reads → silent stale memo** — needs a *mechanism* (declared reads /
   tracked context), since 10-domain transfers pull `pixel_size`/optics metadata.

## A. Data at rest & lazy loading (compressed formats, pyramids, selective full-res ROI, 1D linearization)

This addendum resolves how the v2 lazy Dataset physically stores and streams voxel data so that a **demand-driven pull graph** over 6554×6554 uint16 frames (and 5D M,T,Z,C,Y,X stacks) never materializes a whole frame. It answers the overarching "how is data transferred between nodes" for the image payload — wires carry a lazy `Dataset` whose `image` provider is pulled *per tile*, and content-hash memoization keys become per-tile rather than per-frame — and it grounds the user's three ideas: (1) a compact 1D voxel→component **connectivity map**, (2) **lazy-load compressed for viewing + selective full-res ROI restoration**, and (3) **adaptive-mesh / LOD viewing**. The design reuses what Phase 1 already carved: `Dataset.image: Optional[Any]` (the reserved lazy-provider slot), `AxisSizes(m,t,z,y,x)` (the canonical index model), the `reducers.py` table, and the `coarsen=reduce / refine=broadcast` machinery in `transfer.py`. Note the scope caveat from the codebase survey: the external `nd2studios` backend (`nd2_loader`, `streaming_dataset`, etc.) is *not* vendored in this checkout, and today `nodelab/loading.py` reads everything eagerly into RAM with a hardcoded ND2 `z_projection='max'` (Z is discarded) — so the lazy provider below is a **named-but-unimplemented** target, not an existing capability to wrap.

### A.1 On-disk / streaming storage format

| Route | How it works | Pros | Cons | Maturity | Fit for nodegraph |
|---|---|---|---|---|---|
| **Zarr v3 + sharding** | N-D array as equal chunks, each independently compressed; `sharding_indexed` codec packs many small inner chunks into one shard object w/ trailing index | Small-tile random access at 5D scale without file explosion; native sparse chunks; cheap chunk-level appends; chunk key = natural memo/tile unit | New on-disk dep (no zarr today); per-chunk decode CPU; needs an ingest/transcode step; block-granular (not per-voxel) | battle-tested | **Strongest substrate.** Canonical write target for derived/cached layers + §9 memo checkpoints |
| **OME-Zarr / NGFF** (v0.4 on Zarr2, v0.5 on Zarr3) | Zarr + `multiscales` pyramid convention, named axes, `labels/` subgroup, scale transforms | Free pyramid convention (powers viewer routes); `labels/` = derived-mask story; scale metadata bridges `AxisSizes`/`pixel_size_um` | Only 2–5D t,c,z,y,x model — **no home for m-axis, Point/Track, measurements**; v0.5 reader coverage uneven (see below) | battle-tested (v0.4) | **Viewer/interchange projection of the intensity+label subset only**, not the full Dataset |
| **HDF5 / N5 / BDV** | Single-file (HDF5) or one-object-per-chunk (N5) hierarchical chunked containers + mipmaps | Very mature; BDV = proven TB-scale interactive viewing; imglib2 `CachedCellImg` is the tile-cache pattern to copy | HDF5 single-writer fights an appending graph; C-lib/Java deps; N5 itself now defers to Zarr v3 | battle-tested | Reader **adapter** for existing HDF5/BDV data + design reference; not the write target |
| **TileDB** (dense+sparse fragments) | Dense space-tiles + sparse arrays; writes = immutable timestamped fragments (versioning/time-travel) | Sparse arrays first-class (good for Points); fragments = native append/memo; one engine for dense+sparse | Single-vendor; needs consolidation/vacuum lifecycle; heavier C++ dep; smaller bioimaging footprint | emerging | One targeted **spike for the sparse Point/Track store**; else keep Points as side-car |
| **Cloud-Optimized GeoTIFF (COG)** | Tiled BigTIFF + overviews + tile-index-before-pixels for range reads | Very mature; tiled+pyramided+range-readable | Fundamentally **2D per file** (can't hold 5D); write-mostly; overview gen needs ~⅓ extra temp storage (Create() ~2× is **GDAL 3.13+-specific**, *not* universal) | battle-tested | Narrow: read-only **single-frame export/preview** only |
| **Pyramidal OME-TIFF (SubIFDs)** | Tiled TIFF, pyramid levels in SubIFDs, OME-XML for 5D | De-facto interchange (QuPath/Fiji/napari); **tifffile already a dependency** — zero new dep to read/write | Write-once; no chunk-level incremental append; heuristic axis disambiguation; no sparse/structure domains | battle-tested | **Import adapter + export/interchange** for intensity+label; not the live store |
| **Native ND2 via `nd2` lib** | Proprietary chunked binary, one chunk per m/t/z/c frame; `to_dask()/to_xarray(delayed=True)` | Source format, avoids eager RAM copy; lazy per-frame, **keeps Z** (fixes the max-projection loss); already a dep | **Per-frame chunking only — no sub-frame tile read**; no pyramid; read-only; dask arrays depend on open file / pickle constraint | battle-tested | **Source reader** behind `Dataset.image`; transcode into tiled Zarr for sub-frame ROI |
| **dask / xarray** (compute layer, not a format) | Lazy blocked task graph over any of the stores above | Lazy blocked out-of-core; xarray named dims bridge `AxisSizes` | **Push / whole-subgraph, not per-consumer demand pull**; no persistent per-tile content-hash memo (it *does* ship `tokenize` hashing + opportunistic caching, just not the durable tile store §9 needs) | battle-tested | **Optional per-node compute backend**, NOT the evaluation engine |

**Verified caveats to honor.** Zarr v3 sharding is *accepted* (ZEP-2, 1 Nov 2023) and shipped in zarr-python 3 + TensorStore; the "rewrite-the-whole-shard" worry is an *implementation-support* nuance, not a spec limit — ZEP-2 explicitly permits fixed-order in-place replacement of equal-sized uncompressed inner chunks ([ZEP 2 — Sharding codec](https://zarr.dev/zeps/accepted/ZEP0002.html), [Zarr-Python 3 release](https://zarr.dev/blog/zarr-python-3-release/)). OME-Zarr **v0.5 requires Zarr v3** and is a hard cut from v0.4/v2, and its **reader coverage is uneven today** — Fiji reads v0.5 only after a recent N5 update, napari has an unresolved `zarr<3` vs `zarr>=3` dependency conflict, QuPath 0.6+ reads OME-Zarr but v0.5 conformance is undocumented — so treat "broad ecosystem" as true for **v0.4**, and writing v0.5 as the viewer projection carries real reader-gap risk ([RFC-2](https://ngff.openmicroscopy.org/rfc/2/), [Fiji Zarr3/v0.5 thread](https://forum.image.sc/t/fiji-can-read-and-write-zarr3-ome-zarr-v0-5-new-n5-release/121905), [napari-ome-zarr #139](https://github.com/ome/napari-ome-zarr/issues/139)). The `nd2` **per-frame-only** granularity is confirmed — a 6554² frame is an all-or-nothing read, so sub-frame ROI streaming *requires* transcoding to tiled Zarr first ([nd2 README](https://github.com/tlambert03/nd2/blob/main/README.md)). The nd2 dask **open-file/pickle** constraint (issue #19) is a real, design-relevant hazard — but **issue #19 is CLOSED**, so re-verify against the pinned `nd2` version rather than treating it as a live bug ([nd2 #19](https://github.com/tlambert03/nd2/issues/19)). JPEG-XL/JPEG2000 are **not** first-class Zarr-v3 core codecs (core is none/blosc/gzip/zstd/transpose/crc32c/bytes) — they arrive via `numcodecs`/`imagecodecs` bridges ([numcodecs zarr3](https://numcodecs.readthedocs.io/en/stable/zarr3.html)).

### A.2 Pyramids, LOD & selective full-res ROI (viewer data path)

| **A. Precomputed pyramid + per-level tile cache** (napari / OME-Zarr / neuroglancer model) | Ordered list of 2× downsampled, tiled levels; pick level from zoom, fetch only visible tiles | Canonical fast-view answer; maps 1:1 onto `get_tile(level, ix, iy)`; memo key = `(hash, level, tile)`; bounded RAM | Must build/store pyramid; **downsample reducer is per-domain** (mean for intensity, **nearest/mode for labels**); level-calc has known bugs; 5D → pyramid-per-plane bookkeeping | battle-tested | **Foundational substrate** the Viewer pulls through |

**Verified caveats to honor.** napari does auto-select level by zoom, load only the visible portion, use the coarsest level in 3D, and expose a pin — but the pin setter is **`locked_data_level`** (`data_level` is read-only current level), it is a **recent, version-specific addition** (PR #8917), and the level-calc bug **#4781 is real and open** ([napari image layer](https://napari.org/stable/howtos/layers/image.html), [napari #4781](https://github.com/napari/napari/issues/4781)). The neuroglancer precomputed spec is confirmed (`resolution` non-decreasing with scale index, `grid_size = ceil(size / chunk_size)`, `<xBegin>-<xEnd>_…` unsharded keys, compressed-Morton shards; note the per-scale field is `chunk_sizes`) ([precomputed volume.md](https://github.com/google/neuroglancer/blob/master/src/datasource/precomputed/volume.md)). OME-Zarr downsample **must use nearest/mode for label masks**, and the (2,4,8,16) factors are a *configurable* `downscale=2`-per-level default, not a spec constant ([ome-zarr-py writer](https://ome-zarr.readthedocs.io/en/stable/api/writer.html)). IIIF v3.0 `region` supports absolute `x,y,w,h` and `pct:` rectangles at a chosen `size`, validating the `get_region(...)` mapping ([IIIF Image API 3.0](https://iiif.io/api/image/3.0/)). **Correction on E:** the "fast JPEG2000 effectively needs Kakadu (commercial) or nvJPEG2000 (GPU)" framing is **overstated** — a fast, free, CPU-only path now exists via **HTJ2K (High-Throughput JPEG2000)**, Grok, and multithreaded OpenJPEG, with HTJ2K adopted as a drop-in IIIF replacement; reframe the con as "legacy OpenJPEG Part-1 is slow; use HTJ2K/GPU," not a mandatory license/GPU dependency ([JP2 decode benchmarks](http://chafey.blogspot.com/2016/09/jpeg2000-decoding-performance.html), [nvJPEG2000](https://developer.nvidia.com/blog/accelerating-jpeg-2000-decoding-for-digital-pathology-and-satellite-images-using-the-nvjpeg2000-library/)). **Correction on F:** dask #6668 is a *scheduler task-ordering / independent-graph* memory blowup, **not** a chunk-misalignment over-read of a coarsen reduction — cite it for "add an explicit tile cache," not as proof coarsen over-reads ([dask #6668](https://github.com/dask/dask/issues/6668)). **Uncertain (route D):** "no off-the-shelf library does pinned-ROI mixed-level caching" is only partly true — napari's experimental octree tiled rendering and OpenSeadragon/DeepZoom already do quadtree+LRU tiling; the genuinely novel piece is narrowly the **eviction-exempt full-res ROI overlay**, so lean on existing quadtree+LRU patterns and build only the pin layer.

### A.3 1D linearization & the voxel→component connectivity map (idea 1)

| Route | How it works | Pros | Cons | Maturity | Fit for nodegraph |
|---|---|---|---|---|---|
| **Row-major (C-order) + strides** (baseline) | numpy native flat buffer; offset = Σ index·stride; x-scanline contiguous | Zero-cost/zero-dep; optimal locality along x; free slicing; already what `AttributeLayer.values` assumes | Poor 2D/3D neighbor locality (vertical neighbor = one row-width away); no inherent tiling; not viable whole-frame at 6.5k² | battle-tested | **Correct default — inside a tile.** Not the whole-frame wire payload |
| **Blocked / tiled brick layout** (ImgLib2 `CellImg`/BDV `CellCache`) | Two-level: tile index → brick, row-major within brick; key = `tile·vol + local_offset` | Large cache/TLB win; brick = the memo/pull/cache unit §16 needs; ROI touches only covering bricks; proven at TB scale | Locality only within a tile (edge stencils need halos); tile-size tuning; ragged edge tiles (6554 not power-of-two) | battle-tested | **Strongest fit — the backbone.** `get_frame/get_volume` serves bricks; `execute_transfer` iterates bricks |
| **Morton / Z-order** (bit-interleaved) | Interleave coord bits into one code; near-in-space ≈ near-in-1D | Cheap encode/decode; **prefix = LOD parent** (free pyramid key); dimension-agnostic; good for octrees/sparse Points | Boundary-jump flaw (worse worst-case than Hilbert); adjacency ≠ proximity (range needs BIGMIN); non-2^k wastes index space | battle-tested | **Secondary — ordering key within/across bricks + sparse Point domain**, not the primary dense layout |
| **Hilbert curve** | Adjacency-preserving SFC; consecutive 1D indices always spatially adjacent | Best SFC locality; 1D range ↔ compact spatial cluster (data-skipping) | Expensive/branchy encode; awkward for non-2^k & anisotropic z; marginal over a good brick grid | battle-tested | **Situational** — global spatial-skip index over structure domains only; not dense voxels |
| **Chunked+compressed store w/ sharding** (Zarr v3 / N5) | Persistent brick model; per-chunk codec chain (transpose C/F → bytes → compressor); sharding | Purpose-built; per-chunk compression = "lazy compressed view + full-res ROI chunks" 1:1; multiscale pyramids; chunk key = content-memo unit | New dep/format; per-chunk decode CPU; needs ingest step; block-granular access | battle-tested | **Persistence/streaming layer behind the brick abstraction + §9 checkpoint store** |
| **RLE runs + array union-find CCL** (cc3d) | Store voxel→component map as `(start, length, id)` runs; run-based two-pass CCL, array disjoint-set | **Direct answer to idea (1)**; huge win on piecewise-constant masks; array union-find ~5× faster than pointer-based; runs = mesh-ready vector form; supplies Voxel↔Label bridge executors (fills the `NotImplementedError` seam) | Run length depends on scan order; tile seams need a cross-tile merge; ~4× transient RAM (32-bit); for categorical maps only, not intensities | battle-tested (components) | **The recommended Label-domain + connectivity-map representation**; per-brick CCL + seam-merge as lazy nodes |

**Verified caveats to honor.** Array-based union-find is confirmed **~5× faster** than pointer-based ([LBNL/OSTI CCL](https://www.osti.gov/servlets/purl/887435)); cc3d's ~**4× transient RAM** for 32-bit labels and its run-based SAUF + Tarjan union-find with 6/18/26-connectivity are confirmed ([cc3d README](https://github.com/seung-lab/connected-components-3d)). **Correction (Morton timings) — the widely-quoted "0.03 ms per 256³" figure is REFUTED (a ~1000× units error):** Baert's table is *per whole 256³ volume* in **seconds** — for-loop ~13.1 s, magic-bits ~1.06 s, LUT ~0.32 s; the BMI2 number (~30 ms whole-volume, ≈1.8 ns/code) and LUT ~65 ms come from a comment on a *different* CPU ([Baert Morton benchmarks](https://www.forceflow.be/2013/10/07/morton-encodingdecoding-through-bit-interleaving-implementations/)). The conclusion "encode/decode never bottlenecks the pull engine" still holds with corrected numbers, but note pure-Python `pymorton` is far slower than these compiled figures. **Uncertain — block-layout TLB gains:** the headline "504×" is a *single* 1024×1024 dense-matmul case and the corroborated broad figure is "up to ~93%" (not "91–96%"); **all** these numbers are from dense linear algebra — the magnitude for image *stencil/CCL* workloads on 6554² uint16 is **unverified, prototype to confirm** ([Tiling/block-layout study](https://www.researchgate.net/publication/3300758)). **Uncertain — Hilbert vs Morton:** the "15–40% clustering / 2–4× speedup" figures are global-linearization, workload-specific, and one cited source (arXiv:1606.06133) found Hilbert's overhead *outweighed* its locality on its test system — once data is bricked, the marginal Hilbert win is expected to be small; keep it situational ([SFC locality/energy study](https://arxiv.org/abs/1606.06133)). **Correction — cc3d streaming:** `connected_components_stack` stitches across sequential **Z-sections only**; arbitrary XY **brick** decomposition + cross-brick seam-merge is **not** provided and is bespoke work in the pull graph — label that component "bespoke, not battle-tested."

### Recommended route(s)

Adopt a **layered substrate**, not one format, matching the lazy pull graph at every level:

1. **Brick/tile grid = the backbone** (A.3 blocked layout). A fixed cell (256×256 in 2D, 64³ in 3D) is the unit of the pull engine, the content-hash memo, and the tile cache — the highest-leverage, best-evidenced win and the natural home for ideas (2) and (3). Copy the BigDataViewer `CellCache` pattern (SoftReference-style LRU + low-res-first queue) ([BigDataViewer](https://imagej.net/imagej-wiki-static/BigDataViewer), [arXiv:1412.0488](https://arxiv.org/abs/1412.0488)).
2. **Row-major numpy *inside* each brick** — zero-cost, already assumed by `AttributeLayer.values`.
3. **Provider contract shaped after IIIF/DeepZoom** (A.2 route C): a codec/store-agnostic `get_tile`/`get_region` on `Dataset.image`.
4. **Backing store = on-the-fly dask/zarr coarsen now (A.2 route F), Zarr v3 persisted top levels as optimization (route A)**, choosing the downsample reducer **per domain** (mean/gaussian for intensity, nearest/mode for labels) — this *is* `coarsen=reduce` from `transfer.py`/`reducers.py` applied to viewing.
5. **Selective full-res = pinned-ROI sparse tile cache (A.2 route D)** — the user's idea (2), and the differentiator; pin state stays ephemeral view state so it never dirties the content hash.
6. **Connectivity map = RLE runs + per-brick array union-find CCL (A.3 cc3d)** — the user's idea (1); a true 1D structure that also supplies concrete **Voxel↔Label bridge executors** for the `transfer.py` seam.
7. **Morton** only as an ordering key within/across bricks (its prefix-as-LOD is a free pyramid bonus) and for the sparse Point domain; **Hilbert** reserved for a possible global spatial-skip index over structure domains; **JPEG2000/E deferred** behind the codec-agnostic contract; **dask** kept as an optional per-node compute backend, never the evaluation engine.

**Reuse from the existing codebase:** `Dataset.image` (the reserved provider slot), `AxisSizes.shape_for`/`axis_list` (index model + AXIS_ORDER for the transpose codec), `reducers.py` (per-domain coarsen), the `coarsen=reduce/refine=broadcast` steps in `transfer.py` (same math, now tile-wise), `nodelab/loading.py` axis-normalization + `_enrich_optics` metadata (feeds pyramid scale/pixel-size), and the `nd2` lib's `to_dask`/`to_xarray` as the ND2 source reader (**keeping Z**, fixing today's max-projection loss).

### Integration into the V2.00 plan

**Where it lands.** A new `nodegraph/provider.py` (the lazy tiled image provider + tile cache) plus extensions to `nodegraph/dataset.py` (structure-domain `AttributeLayer` layout for RLE labels). It is the concrete implementation of the plan's §3.1 `get_frame/get_volume` provider and the §9 pull + content-hash memo engine, and it satisfies the §16 "tile-aware, not whole-frame" mandate. **Phase-wise:** provider contract + brick cache + on-the-fly coarsen land in **Phase 2** (the lazy pull engine) since the memo unit *is* the brick; the RLE connectivity map and Voxel↔Label bridge executors extend **Phase 2/3** where `BridgeStep` execution (today `NotImplementedError`) is filled in; the pinned-ROI viewer policy and optional GPU render tail belong to the **Phase 5 GUI/Viewer** node.

**Provider protocol sketch** (codec-agnostic, IIIF-shaped, brick-serving):

```python
# nodegraph/provider.py
TileKey = tuple  # (channel:int, m:int, t:int, z:int, level:int, iy:int, ix:int)

class LazyImageProvider(Protocol):
    axes: AxisSizes                       # canonical index model (reuses dataset.py)

        ...                                                # composes get_tile + resample

```

**Memo key** (turns the whole-frame memo into a tile-aware one, per §16):


**Pinned-ROI viewer request** (idea 2): the Viewer node emits `{viewport_rect, target_zoom, pin_rects}`; the provider serves mixed-level tiles (coarse-from-coarsen + pinned level-0), backed by a pin-exempt LRU (`cachetools.LRUCache` with a manual pin set).

**Connectivity-map attribute layer** (idea 1) — a structure-domain `AttributeLayer` whose `values` is not a dense array but a run table, one per brick, with a cross-brick equivalence merge:

**New open questions (require a benchmark before committing):**

- **Brick size / codec tuning:** does Zarr v3 sharding + per-chunk compression actually hit *interactive* latency on 6554² uint16 and 5D stacks? Decode CPU per chunk and chunk-size are the risk — this is design-intent, **not yet benchmarked** on this data.
- **Block-layout gains on image workloads:** confirm the cache/TLB win magnitude carries from dense linear algebra to image stencils/CCL at 6.5k² (the literature figures do not transfer automatically).
- **Cross-brick CCL seam-merge:** cc3d only stitches sequential Z-sections; the XY brick seam-merge is **bespoke** — validate correctness and peak RAM (per-tile CCL should keep the ~4× transient factor well below the whole-frame cost).
- **OME-Zarr version choice:** write **v0.4** for the viewer projection now (broad reader support) and gate v0.5 on napari/QuPath catching up, given the `zarr<3`/`zarr>=3` split.
- **`nd2` dask stability:** re-verify the open-file/pickle constraint (issue #19, now closed) against the pinned `nd2` version before relying on lazy nd2 arrays inside a parallel/cached pull; the safe fallback is staging to Zarr.
- **Anisotropic z:** the pyramid needs **per-axis** scale factors (z_step ≠ xy), not a scalar — reflect this in `level_shape` and the OME-Zarr `coordinateTransformations`.

## B. Pixel connectivity, compact labels & vectors/meshes from connectivity

This cluster answers the user's idea (1): *categorize/register pixels by CONNECTIVITY before X,Y,Z to form vectors / 2D-3D representations via a connectivity map stored as a 1D array*. In nodegraph v2 terms, the "connectivity map" is the concrete, still-unspecified layout for the **Label / Point / Track** structure domains in `nodegraph/dataset.py`, and the executor for the **Voxel↔Label / Label↔Point** bridges that `nodegraph/transfer.py` currently stubs with `NotImplementedError`. Two sub-problems fall out: (B1) how to *encode* the connectivity map compactly enough to ride on a lazy `Dataset` wire and decompose to tiles/linear ranges; and (B2) how to *turn that map into vectors/meshes* (boundaries, chain codes, skeletons, iso-surfaces, displacement fields) for the constructive "Fill/Extract Boundary" bridge and the viewer. Every route below is judged against the tile-aware lazy-pull + content-hash memo engine (V2.00 plan §9, §16), whose hard constraint is: **no whole-frame passes on 6554² frames — everything must key by tile.**

### Recommended route(s)

**Adopt a LAYERED representation, not one encoding.** The pieces compose because every one of them decomposes to tiles or linear-index ranges.

- **Backbone model — Route B1-1 (flat 1D linear index + voxel→component map).** This is the literal "categorize by connectivity before x,y,z as a 1D array." Label = sorted index list; Point = index + subpixel + optional vector; Track = ordered member ids over the Timepoint axis. It maps 1:1 onto `dataset.py`'s element-indexed `id→value` `AttributeLayer` and turns `transfer.py` bridges into sorted-index merge-joins with clean memo keys. **Keep indices tile-local.** Arithmetic (verified): a single 6554² frame = 42,954,916 indices = ~172 MB as uint32, which *fits* in uint32 (max 4.29 B); overflow is purely a Z·T·M product effect (Z ≳ 100 alone overflows). So tile-local keys stay 32-bit by construction, not as a workaround. [numpy ravel/unravel](https://numpy.org/doc/stable/reference/generated/numpy.ravel_multi_index.html)

- **Producer — Route B1-2 (CCL).** `scipy.ndimage.label` / `skimage.measure.label` as the zero-dependency, Qt-free default (already vendored); **cc3d** as the perf upgrade because it hands you the region graph + per-region stats + memmap for free. *Honest scoping of the cc3d speedup:* the "orders of magnitude over scipy" figure holds only for **densely multilabeled** data compared to running scipy per-label; for a **single** labeling call cc3d is ~1.3–1.4× faster (512³: scipy 1.31 s vs cc3d 0.95 s). [cc3d README](https://github.com/seung-lab/connected-components-3d/blob/master/README.md)

- **Shape-selected serializations behind the lazy provider:** **RLE / RLEMaskLib** for blocky Label footprints + on-wire mask algebra ([pycocotools mask](https://github.com/cocodataset/cocoapi/blob/master/PythonAPI/pycocotools/mask.py), [RLEMaskLib](https://rlemasklib.readthedocs.io/)); **pydata `sparse` COO** for the Point domain and sparse Label sets (scipy.sparse is 2-D only — verified) ([pydata sparse](https://sparse.pydata.org/en/stable/)); **compressed_segmentation** as the tile-addressable backing for a large Voxel labelmap — **block IS the tile**, unique per-block partial decode ([neuroglancer volume spec](https://github.com/google/neuroglancer/blob/master/src/datasource/precomputed/volume.md)). *Correction to honor:* its per-voxel index width is quantized to `{0,1,2,4,8,16,32}` bits (`ceil(log2(#distinct))` rounded **up** to an allowed width), and the data-dependent block-size cap stems from the 24-bit `lookupTableOffset` limiting total block payload.

- **Relationships — Route B1-7 (RAG).** Executes the stubbed Label↔Label / structure bridges as a compact node/edge attribute; a **temporal RAG over the Timepoint axis is the Track linkage.** Build from cc3d's contact graph (tile-stitched).

- **Vectors/meshes:** default 2D boundary = **`find_contours`** (sub-pixel, per-region); use **OpenCV chain codes** when you want the compact 1D encoding + hole hierarchy on the wire; 3D = **multi-label Surface Nets via VTK/PyVista** (not per-label MC); **QEM decimation** as the LOD engine for the viewer (ideas 2 & 3); **skan** for filaments; **Delaunay/Poisson** for the Point→mesh/field direction; **DIC/DVC** for the temporal displacement-vector bridge.

- **Cold storage only — Compresso.** Reserve for archival/checkpoint blobs; *constraint to honor:* its Z-slice random access is a format-v1 feature and is **not available for 6-connectivity** (slices interdependent), reinforcing "cold storage, not live compute." [seung-lab/compresso](https://github.com/seung-lab/compresso)

**Reuse from the existing codebase:** the label id array *is* the mask that defines Label membership, so `skimage.measure.regionprops` fills Label `AttributeLayer`s (centroid/bbox/area/moments) directly — this is the concrete executor for the currently-stubbed Voxel↔Label bridge (`mean-in-mask` / `paint-by-label`) in `nodegraph/transfer.py`. The `nodegraph/reducers.py` NaN-aware table extends to segment/group reducers; `Dataset.with_attribute`'s shape-validation is exactly where a tiled/lazy structure layer relaxes the eager numpy check.

### Cross-cutting risk (must design for)

CCL, boundary tracing, skeletonization, and marching-cubes/surface-nets are **all inherently whole-region and break at tile borders.** `scipy`/`skimage` `label()` is single-pass whole-array; tile-local correctness requires *your own* block-based union-find **border-merge** pass (well-established in the literature but **not** provided out of the box, and **not** auto-done by cc3d across independently tiled subvolumes). `find_contours` leaves edge-touching contours **open**, so a region clipped by a tile boundary yields an open polyline the same stitch step must close. Marching cubes / surface nets are whole-volume and memory-heavy — scope them to a selected label sub-volume or an explicit "materialize this ROI" node, never a default streaming op. [Block-based union-find labeling (ICIAP 2019)](https://www.federicobolelli.it/media/publications/pdfs/2019iciap_labeling.pdf), [find_contours docs](https://scikit-image.org/docs/stable/auto_examples/edges/plot_contours.html)

### The pixel-connectivity data-reshape method (the well-known technique)

Your instinct — "register pixels by *connectivity* before X,Y,Z, form vectors / 2D-3D representations from that connectivity map, and store it as a 1D array" — is not a novelty; it is the founding idea of an entire family of canonical data structures. The common thread: **values (or point coordinates) live once in a flat 1D array, and geometry/topology is *derived* from a second flat 1D index/connectivity array**, rather than stored densely on a grid. This complements (does not repeat) the CCL/RLE/compressed-segmentation label-encoding angle: those compress *which label a pixel has*; these reshape *how pixels relate to each other*.

#### Routes comparison

| Route | How it works (concretely) | Pros | Cons | Maturity | Fit for nodegraph |
|---|---|---|---|---|---|
| **1. im2col / im2row ("unfold")** | Reshape by *local pixel connectivity*: each k×k(×C) neighborhood is flattened into one column/row of a 2D matrix so convolution becomes one dense GEMM. PyTorch `nn.Unfold` produces `(N, C·∏kernel, L)`; docs note 2D case "is sometimes called im2col" ([Unfold — PyTorch](https://docs.pytorch.org/docs/2.7/generated/torch.nn.Unfold.html)). | Turns conv into one BLAS GEMM; simple; generic ([NVIDIA Conv Guide](https://docs.nvidia.com/deeplearning/performance/dl-performance-convolutional/index.html)). | Data duplication (~k² per pixel at stride 1); large scratch buffer. Good for a lazy "neighborhood → feature vector" node on Voxel; not how the Dataset persists. |
| **2. Image → graph connectivity matrix** | Each pixel/voxel a graph node; edges connect neighbors. sklearn `grid_to_graph` → pixel connectivity graph, `img_to_graph` → gradient-weighted, both **sparse adjacency** (`coo_matrix`) ([grid_to_graph](https://scikit-learn.org/1.5/modules/generated/sklearn.feature_extraction.image.grid_to_graph.html), [img_to_graph](https://scikit-learn.org/stable/modules/generated/sklearn.feature_extraction.image.img_to_graph.html)). | **3. CSR / CSC sparse grid-graph** | Adjacency as **three flat 1D arrays**: `data`, `indices`, `indptr` (row offsets). CSR column-slice slow (use CSC). | Very mature (Netlib mid-90s; SciPy/cuSPARSE standard). | **Canonical on-wire form** for any Label-RAG, Track lineage graph, or Point k-NN graph. Identical to FEM node-coords + element-connectivity ([FElupe mesh](https://felupe.readthedocs.io/en/v8.1.0/felupe/mesh.html)). | Geometry once, no duplication; arbitrary cell types; the literal "1D array, geometry derived from connectivity"; interchange-standard (VTK/meshio/PyVista). | Topology-only; needs companion attribute arrays; not for random pixel-grid queries. | Battle-tested (VTK/FEM decades; VTK 9 current). | **Closest literal match.** Points array = **Point domain** (x,y,z once); Cells/Connectivity = how points form vectors/boundaries/tracks. **Point↔Label Fill/Extract-Boundary bridge** = extract a boundary cell (polyline/polygon of point-indices) from a Label region. |
| **5. Half-edge / DCEL / winged-edge** | Connectivity-*first* topology: each half-edge records `twin`, `next`, `origin`, `face`; O(1) local traversal without dense adjacency ([CGAL HalfedgeDS](https://doc.cgal.org/latest/HalfedgeDS/index.html); [CS184](https://cs184.eecs.berkeley.edu/sp19/article/15/the-half-edge-data-structure)). | Ideal for *editing* topology (split/merge/traverse boundaries) & vector 2D/3D reps; geometry detachable. | Restricted to **orientable 2-manifolds** — cannot represent non-manifold (two cubes sharing a vertex); quad-edge/partial-entity lift that ([CGAL ref](https://doc.cgal.org/latest/HalfedgeDS/group__PkgHDS.html)). Complex. | Battle-tested (CGAL, OpenMesh, Blender BMesh). | Fit for **editable vector Label boundaries** (polygons) and the boundary-bridge's editing side. Overkill for bulk voxel data. |
| **6. Connectivity-driven reordering (RCM / nested dissection / SFC)** | A **permutation** of a 1D connectivity map for locality. RCM clusters nonzeros near the diagonal ([SciPy RCM](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csgraph.reverse_cuthill_mckee.html)). Nested dissection partitions by separators ([MATLAB dissect](https://www.mathworks.com/help/matlab/ref/dissect.html)). SFCs (Morton/Hilbert) linearize n-D→1D preserving neighbors ([Z-order vs Hilbert](https://gupea.ub.gu.se/server/api/core/bitstreams/86ce5d0a-3f6c-420b-b215-c286968ebee0/content)). | Cache-locality / solver-fill wins on the *same* arrays; SFC gives chunk-friendly 5D layout. | Reordering cost; carries a permutation map; Z-order has boundary "jumps." | Mature (RCM 1969, ND 1973, SFCs standard). | **Layout optimizer** for the Dataset's flat arrays: SFC-linearize the 5D (M,T,Z,C,Y,X) volume, RCM-order Label/Track graphs, so lazy pull + content-hash memoization touch contiguous memory. |

#### Best match to the user's description

"Connectivity before X,Y,Z → form vectors / 2D-3D reps → stored as a 1D array" matches the **flat points-array + connectivity-array family: VTK `vtkCellArray` / FEM element-connectivity (Route 4), with CSR (Route 3) as its pure-graph sibling.** The "x,y,z live *once*, geometry *derived* from connectivity" phrasing is precisely VTK/FEM Points+Cells: coordinates one time in a Points array + a flat `Connectivity`(+`Offsets`) array of integers indexing them to construct vectors/polygons/volumes on demand. When "values" are scalar edges not points, the identical idea is CSR's `indptr`/`indices`. So **VTK-cell-array / CSR are the headline match**; image→graph (2) is how you *build* the connectivity from pixels; half-edge (5) is the editable-topology upgrade; RCM/SFC (6) is the locality optimizer; im2col (1) is the alternative to note, not the match.

#### How it lands in the plan

Represent **Point** as a flat coordinates layer (x,y,z once) and **Label/Track** connectivity as CSR triples (`data/indices/indptr`) — three arrays, trivially **content-hashable** and cheap to memoize, so demand-driven pull rehydrates a graph only when inputs change. The **Point↔Label Fill/Extract-Boundary bridge** becomes a first-class cell op: *Extract Boundary* emits a Cell (polyline/polygon of Point indices) from a Label region — a VTK-style connectivity array over the Point coordinate layer — and *Fill Boundary* rasterizes that indexed cell back to Voxel/Label. Build the pixel graph with `grid_to_graph`/RAG semantics (Route 2), persist as CSR/points+cells (Routes 3–4), reach for half-edge only where users edit vector contours (Route 5), and apply SFC linearization + RCM ordering (Route 6) so memoized pulls stay cache-local on 6554² frames.

#### Rigor notes (from the agent's adversarial self-check)
- im2col is *not* the sole modern conv method — cuDNN also selects implicit GEMM / Winograd / FFT to avoid the materialized buffer.
- "~k² duplication" is an approximate upper bound (stride/padding/dilation dependent).
- Hilbert > Z-order for locality is supported but nuanced (Z-order cheaper, "good enough" for caching).
- im2col origin attributed to Chellapilla–Puri–Simard 2006 is **(unverified)** — primary not fetched.
- Half-edge orientable-2-manifold-only and VTK 9 Offsets/Connectivity layout: independently corroborated.

## C. Adaptive-mesh 2D viewer & GPU streaming

This cluster addresses the user's ideas (2) *selective full-res ROI* and (3) *adaptive meshing of the 2D viewer* — plus the "how is data transferred to the viewer" question — by making the viewer a **pure demand-driven pull consumer** of the lazy `Dataset.image` provider. The viewer computes, per paint, which resolution level and which tiles its current transform requires, and pulls exactly those backward through the graph; the Phase‑2 content-hash memo caches at that same tile granularity, satisfying the V2.00 §16 mandate that the engine be *"tile-aware, not whole-frame."*

**Scope correction up front.** A single 6554×6554 uint16 frame is only ~85 MB and sits *below* the common 16384‑texel GL max-texture-size — it fits in **one** GPU texture and needs no tiling to display. The real scaling pressure is the **5D M×T×Z×C multiplication and cross-stack memory bounding**, not any one frame. Tiling/streaming is therefore justified by 5D streaming and memory limits, *not* by frame size; motivations that invoke "exceeds max texture size" do not apply at 6.5k².

Today the repo has none of this: `nodelab/panels/viewport_panel.py` `_ImageField.paintEvent` holds one whole-frame array and does a full `QPixmap.scaled()` software rescale on *every* repaint, with no pyramid, tiling, GPU path, pan/zoom, or LOD.

### Verification notes (corrections honored)

- **napari octree is gone.** napari v0.5+ **removed** `NAPARI_OCTREE`/`NAPARI_ASYNC` (`OctreeImage`/`TiledImageVisual`/`TextureAtlas2D`) in favor of NAP‑4 "async slicing," which does **not** yet do progressive tiled fetch/render ([napari rendering guide, dev](https://napari.org/dev/guides/rendering.html); [napari#2712](https://github.com/napari/napari/issues/2712); [napari#5561, still open](https://github.com/napari/napari/issues/5561)). The 0.4.19 docs describe deleted code — treat Route 2 as a **reference pattern to reimplement on VisPy/QOpenGLWidget**, not a dependency.
- **HW sparse effectively unavailable on Apple.** Apple deprecated OpenGL (frozen at 4.1) in 2018, so there is no GL sparse path on macOS; and `MoltenVK` sparse-residency support is incomplete ([MoltenVK#1700, open](https://github.com/KhronosGroup/MoltenVK/issues/1700)), native Metal only gaining sparse in 2.3 / "placement sparse" in Metal 4 (2025). "Vulkan+MoltenVK" is **not** a clean fallback — **Route 5 stays deferred** ([ARB_sparse_texture spec](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_sparse_texture.txt)).
- **tifffile zarr reads are the *secondary* path only.** `tifffile` can do per-tile/pyramidal region reads via `ZarrTiffStore` (`aszarr`/`return_as='zarr'`) *without* full `imread` — **but only for genuinely tiled & pyramidal TIFFs**, and newer versions pull in a zarr‑3 dep not in `requirements.txt` ([tifffile on PyPI](https://pypi.org/project/tifffile/); [tifffile#134](https://github.com/cgohlke/tifffile/issues/134)). Decisively, this repo's **primary format is ND2**, loaded via the `nd2` library — tifffile's zarr path does nothing for ND2. **The tile-addressable provider must be built on ND2's own lazy/dask interface for the main path.**
- **Route 3 chunk shape is configurable, not fixed.** Neuroglancer/zarr `chunk_sizes` accepts multiple shapes incl. anisotropic `256×256×1`, so authoring the store with display-friendly chunks **avoids** any re-tiling layer; re-tiling is only forced when consuming a pre-existing 64³ volume dataset ([precomputed volume.md](https://github.com/google/neuroglancer/blob/master/src/datasource/precomputed/volume.md); [tensorstore driver](https://google.github.io/tensorstore/driver/neuroglancer_precomputed/index.html)). Present as conditional, not inherent.
- **CPU-vs-GPU renderer decision is UNVERIFIED (empirical).** No external source establishes a hard 6.5k² threshold where a tiled `QGraphicsScene` (one `QGraphicsPixmapItem` per tile, free frustum culling) fails and `QOpenGLWidget`/VisPy becomes mandatory. Given a single frame is only ~85 MB, the CPU tiled path could plausibly go a long way. **Prototype/benchmark before committing to a GPU rewrite** (local: `nodelab/panels/viewport_panel.py:70`).

### Recommended route(s)

**Adopt a layered design, not one route:**

1. **Baseline renderer = Route 1** (mip-pyramid + quadtree tile streaming). Lowest risk, satisfies the §16 tile-aware pull directly. Reuse the existing panel chrome, `numpy→QImage(Grayscale8)→QPixmap` pipeline, and `set_frame`/`set_channels`/`set_source` host API from `nodelab/panels/viewport_panel.py`; lift the proven **wheel-zoom-to-cursor (AnchorUnderMouse) + left-drag pan + `zoomChanged`** interaction from `nodelab/canvas/view.py`; keep `ZOOM_MIN/ZOOM_MAX`, `VIEWPORT_BG`, `mono_font` from `nodelab/theme.py` and HiDPI `scaling.s()`. Only the `_ImageField.paintEvent` seam is replaced.
2. **On-disk/cache tier = Route 3, concretely OME‑Zarr/NGFF** (precomputed as format blueprint) — per-chunk content hashes as memo keys and the only clean **true‑3D (Z) volume** streamer, fixing today's hardcoded `z_projection='max'` MIP in `nodelab/loading.py` that discards Z.
3. **GPU render/loading model = Route 2** (texture-atlas coarse-to-fine + async ChunkLoader on VisPy/QOpenGLWidget) — adopt **only if** the CPU tiled `QGraphicsScene` prototype can't hold framerate. napari is reference, not dependency.
4. **Wrap everything in Route 7** (LRU tile cache under a VRAM/RAM budget), **unified with the Phase‑2 content-hash memo store** so a tile decoded for display is the same artifact the graph reuses; **pin** ROI full-res tiles.
5. **Route 6 only for the 2.5D/3D intensity-surface view** and to force deeper subdivision at a selective full-res ROI (idea 2); it composes with Route 1 tiles as the texture source.
6. **Defer Routes 4 & 5** (software/hardware sparse virtual textures) — revisit only if the viewer must composite *many* gigapixel layers into one surface simultaneously.

**Non-negotiable enabler:** redefine the `Dataset.image` provider protocol to be **tile/chunk-addressable** — `(level, m, t, z, c, ty, tx)` returning a bounded tile, *not* whole frames — so all adopted layers pull the same granularity and share one memo/cache.

### Integration into the V2.00 plan

**Where it lands.** Split across two seams already carved in the codebase:

- **`nodegraph/dataset.py` → the reserved `image: Optional[Any]` slot** becomes a concrete tiled provider protocol (Phase 2, alongside the pull engine). This is the §3.1 `get_frame/get_volume` provider and §11 `ctx.image(channel=...)` seam, currently a typed placeholder.
- **`nodelab/panels/viewport_panel.py` → `_ImageField.paintEvent`** becomes the tiled/LOD draw path (GUI phase). The panel chrome, channel chips, and host API stay.
- **Phase‑2 memoization engine** and the viewer's tile cache are the **same** LRU-bounded store (Route 7).

**Provider protocol sketch** (built on ND2's lazy/dask interface for the primary path; tifffile‑zarr for the secondary TIFF path):

```python
# nodegraph/dataset.py — the concrete home for Dataset.image
class TileKey(NamedTuple):
    level: int          # pyramid level, 0 = full res
    m: int; t: int; z: int; c: int
    ty: int; tx: int    # tile row/col at this level

class LazyTileProvider(Protocol):
    tile_shape: tuple[int, int]           # e.g. (256, 256)
    def levels(self) -> int: ...          # pyramid depth
    def grid_size(self, level: int) -> tuple[int, int]:  # (n_ty, n_tx)
        ...
    def get_tile(self, key: TileKey) -> np.ndarray:      # bounded (<=256x256)
        ...                                              # NEVER whole-frame
    def content_hash(self, key: TileKey) -> bytes:       # memo key, cheap
        ...
    # true 3D — the Z-fix; returns a bounded sub-volume, not a MIP
    def get_subvolume(self, level, m, t, c, z0, z1, ty, tx) -> np.ndarray: ...
```

**Memo key.** The pull engine already plans/executes per-array in `nodegraph/transfer.py`; make its content-hash key incorporate `TileKey` so a Voxel-domain field evaluates and memoizes **per tile**, not per whole frame. `AttributeLayer.values`' eager shape-validation in `Dataset.with_attribute` must be **relaxed for tile-backed Voxel layers** (validate tile shape on demand, not the full 6.5k² array at add time).

```
memo_key = content_hash(node_op, params, upstream_hashes..., TileKey)
tile_cache[memo_key] -> decoded/processed np.ndarray   # shared by viewer + graph
```

**Viewer pull loop** (per paint, pure consumer):

```python
level, (ty0,ty1,tx0,tx1) = lod_for(self.transform, provider)   # from own zoom
for ty, tx in visible_tiles:
    key = TileKey(level, m, t, z, c, ty, tx)
    tile = pull(provider, key)          # backward through graph → memo → provider
    draw(tile, at=tile_screen_rect)     # coarse cached tile as placeholder first
# ROI full-res: force level=0 tiles inside the ROI rect, pin them in cache
```

**Selective full-res ROI (idea 2)** = force `level=0` `get_tile` calls inside the ROI rectangle and **pin** those keys in the Route‑7 cache so they survive eviction; everything else stays at the zoom-appropriate level. **Adaptive meshing (idea 3)** for the 2.5D surface = restricted-quadtree subdivision where screen-space error or the ROI mask demands it, each node textured from the matching pyramid tile — the subdivide decision *is* the choice of which `(level, tile)` to pull.

**New open questions:**

1. **CPU vs GPU renderer** — *unverified.* Benchmark a tiled `QGraphicsScene` (pixmap-item-per-tile culling) at 6.5k² across 5D before committing to a `QOpenGLWidget`/VisPy rewrite.
2. **Pyramid generation** — build offline (OME‑Zarr via `bioformats2raw`) vs on-the-fly downsample on first pull? ND2 has no native pyramid; the `nd2`/dask lazy interface must supply coarse levels somehow (dask coarsen vs precomputed store). Adds a `zarr`/`dask` dependency (not currently in `requirements.txt`).
3. **Chunk granularity** — one chunk shape for both 3D volume streaming and 2D display (author anisotropic `256×256×1`), or two tiers with a re-tiling layer? Conditional on whether inputs are self-authored vs pre-existing volumes.
4. **Memo ↔ eviction lifetime** — coordinating LRU eviction with pull-engine liveness so a tile the graph still needs downstream is never evicted (needs a refcount/pin from active pulls).
5. **Z projection policy** — the provider must expose *both* per-slice `get_tile` and MIP-on-demand, replacing today's load-time hardcoded `z_projection='max'` in `nodelab/loading.py`; where does the projection choice live — provider param, node, or viewer control?

## D. Node-to-node data transfer, lazy pull eval & memoization/out-of-core

This section resolves how the locked nodegraph v2 design — a single immutable `Dataset` flowing on the thick wire, lazy demand-driven pull, and content-hash memoization — should actually be built in Phase 2, on top of the Phase-1 core (`nodegraph/dataset.py`, `domains.py`, `transfer.py`, `registry.py`). The goal is a Qt-friendly, numpy-native engine that (a) moves a `Dataset` between nodes without copying its big attribute buffers, (b) evaluates only the nodes and only the *tiles* a viewer/export actually pulls (the 6554×6554 single-frame reality forbids whole-frame work), and (c) memoizes results per tile so pull fan-out and interactive T/Z scrubbing stay cheap. It splits into three sub-problems: the on-wire payload, the pull-evaluation engine, and the memo/cache/out-of-core store. Every route below is judged against a lazy `Dataset` whose `image: Optional[Any]` slot is a not-yet-implemented voxel provider.

### Recommended route(s)

Build the Phase-2 engine as a **hybrid coarse-pull / fine-push tile engine**, layering four picks:

1. **On-wire (D.1): Blender-style implicit sharing on top of the existing immutable `Dataset`.** Attach a small refcount + `mutable` flag to `AttributeLayer.values` so a single-user layer mutates in place and a shared one copies-on-write via a `values_for_write()` accessor. This keeps `with_attribute`/`with_layer` cheap *and* safe under concurrent pull, and answers "how data moves between nodes without copying." *Reuse:* `nodegraph/dataset.py`'s frozen dataclasses + structural sharing are already 90% of this; the frozen-object identity becomes the free upstream-change signal. *Note:* atomicity of the refcount is a **must-verify** engineering item for the concurrent pull scheduler — the safety argument depends on it (Blender uses `std::atomic`; a Python port must add the equivalent guard).
   - Represent **structure domains (Label/Point/Track) as columnar tables** — numpy structured arrays now, Arrow RecordBatches only if/when they grow large or must cross a process boundary (in-process C-Data zero-copy to the viewer). Do **not** route structure domains through the tile/array path.

2. **Eval engine (D.2): the ilastik-lazyflow ROI-pull pattern, hand-rolled Qt-friendly.** It is the single closest published precedent to the locked design. Pull at **node + tile granularity, never per-pixel**; each node's `evaluate(ctx)` pulls only the upstream tiles it needs; inside a tile, fuse/push elementwise field ops (Blender-field + Halide-`compute_at` style) so we never pay per-pixel pull dispatch. Replace lazyflow's greenlet scheduler with a thread-pool + future model that co-exists with the Qt event loop. *Reuse:* `plan_transfer` router + `SocketSpec.domain` field hook already exist; `execute_transfer`/`_apply_lattice_step` (today whole-array) become the tile-aware seam.

3. **Image layer (D.2): `Dataset.image` as a Python CachedCellImg analog.** A tile grid over `(m,t,z,c,y,x)` whose cells are produced by a loader that either reads the backend or **computes** (projection / pyramid level / field). This one mechanism serves all three user ideas — selective full-res ROI = a full-res loader over a chosen interval composited over a coarse pyramid tile; adaptive-mesh viewer = load only visible cells at the zoom-demanded LOD (as BigDataViewer does). *Reuse:* the eager reader + axis-normalization in `nodelab/loading.py` (its `read_nd2_metadata` + per-channel `load_nd2_timeseries` call pattern) is the reference a lazy loader wraps — but note Z is currently discarded by a hardcoded `z_projection='max'`, which a real volume provider must stop doing.

4. **Memo/store (D.3): a lazy-lineage content-hash memo + two-tier byte-budgeted cache.** Key = `H(op_key, canonical params, calibration subset, tuple(upstream keys))` — hash the **recipe, not the pixels**, so no lazy `Dataset` is materialized to look up a hit. Layer Salsa's three ideas: revision-based O(depth) validity, **cutoff/backdating** (stop the ripple when output is unchanged — e.g. a LUT recolor), and **durability tiers** (mark the ND2/TIFF loader + calibration high-durability). Store = a scan-resistant **2Q/cachey cost-aware RAM tile cache** keyed `(memo-key, tile-index)` (avoid patent-encumbered ARC), spilling to a **memmap → Zarr** disk tier keyed by the same content hash for cross-session auto-checkpoints.

**Why this pick:** it is the only combination that satisfies the locked constraints *and* the 6.5k² tiling mandate (V2.00 §16) without vendoring a foreign runtime. Memoization is **mandatory, not optional** — pull fan-out otherwise recomputes shared upstream work. Two verified constraints shape the memo design and must not be papered over:
- **`dask.base.tokenize` is REFUTED as a persistent cross-session key** — Dask documents determinism holds only *within one interpreter session*, "not guaranteed across interpreters" or versions. Use it (or a model of it) for **in-session dedup only**; build the durable auto-checkpoint key from a **self-controlled stable hash** (pinned BLAKE3/xxhash over raw tile bytes + op identifier + canonical params).
- **Blender fields DCE is best-effort, not a guarantee** — anonymous attributes are "often only computed when needed" and cleaned up *after* evaluation; do not bank hard memory-savings claims on "never materialized," treat it as heuristic lazy eval + post-eval cleanup.

**Open questions (new, flagged as uncertain):**
- **Tile size vs domain axes.** Cell/tile shape is chosen up front (CachedCellImg caveat); the right default over a 5D `(M,T,Z,C,Y,X)` lattice — and whether it must differ per domain — is unresolved. Bad chunking hurts both read amplification and compression ratio.
- **Cutoff fingerprint cost.** Backdating needs a cheap output fingerprint, but computing it requires materializing at least a sampled tile — the sampling policy that makes cutoff cheaper than just recomputing is unverified for our ops.
- **Non-deterministic ops break the content-hash contract.** RNG and threaded float-reductions (non-associative) violate "same key ⇒ same output." Which node categories must be marked non-memoizable is undecided.
- **Structure-domain bridge execution + connectivity layout.** The 1D connectivity-map layer (idea 1) and the `BridgeStep` executors (label↔voxel, point-in-label, track linkage) are named but unspecified in code; their exact array layout and how they participate in tile-aware pull is open.
- **Refcount atomicity in Python.** The concurrent-pull safety argument for implicit sharing depends on an atomic refcount; whether a GIL-backed counter suffices or a real lock/atomic is needed must be settled before parallel evaluation lands.
- **Provider Z-restoration.** The current bridge discards Z via a hardcoded max projection; the lazy provider must expose full volumes, requiring the external `nd2studios` backend's real `get_frame/get_volume` axis/projection contract — **not present in this checkout** and must be sourced before the image layer can be finalized.

## 1. Missing routes a world-class design would weigh

**Storage / lazy load (Addendum A):**
- **Blosc2 NDim (b2nd)** — the single biggest omission. Numpy-native, zero format-conversion, SIMD, and its **double partitioning (blocks within chunks)** is *literally* idea (2): coarse block read for viewing + full-res sub-block ROI, without a Zarr ingest step. You evaluated Zarr/HDF5/TileDB/COG/OME-TIFF/nd2 but skipped the one built for in-memory compressed n-D numpy.
- **Compression *tuning* for uint16** never appears: Blosc + **bitshuffle + zstd** is the microscopy default and swings ratio/throughput by >2×. You debate formats but never the codec chain inside them.
- **TensorStore** is mentioned in passing but never scored as a route — it already unifies zarr3/n5/neuroglancer with async + its own bounded cache and would subsume half of D.3's hand-rolled store.

**Eval engine (D):**
- **Cancellation / structured concurrency** — no route addresses that fast T/Z scrubbing must *cancel* in-flight pulls. This is the dominant interactivity cost and is absent from D.2.
- **Prefetch/backpressure scheduling** named but no concrete route (priority queue by viewport distance, speculative ring prefetch).
- **Glitch-freedom** in pull+memo dataflow (partial invalidation serving inconsistent tiles mid-update) is unmentioned; lazyflow's own "under-reported dirty region" bug is exactly this and you flag it but don't design against it.

**Viewer (C):**
- **QRhi / QRhiWidget (Qt 6.7+)** — the biggest viewer omission. You deferred HW-sparse citing macOS OpenGL deprecation, but PySide6 ships **QRhi**, Qt's own abstraction over Metal/Vulkan/D3D/GL. That is the intended cross-platform GPU path and dissolves the very portability objection that killed Route 5. You jumped straight to VisPy.
- **pyqtgraph** — the incumbent scientific-Qt image viewer (`ImageItem`, 16-bit LUT, downsampling, ROI) is never evaluated. `QGraphicsView.setViewport(QOpenGLWidget)` (GL-accelerated scene, free culling) is also skipped between the CPU and full-VisPy options.

**Connectivity/meshes (B):** **Euclidean distance transform + watershed** (seung-lab `edt`) as the Point→Label seeded-segmentation bridge; **GPU CCL** (cuCIM) for the compute backend. Both plausible producers, both absent.

**Cross-cutting:** the **measurements domain** and the **value/field socket layer** are barely served anywhere — every section optimizes image+label, partially Point/Track, and drops the other two.

## 2. Unverified / hand-wavy claims still standing

- **"Brick = highest-leverage, best-evidenced win"** (A, Recommended §1) directly contradicts A's own verified caveat that block-layout TLB gains are *"unverified for image stencils/CCL, prototype to confirm."* Cannot be both best-evidenced and unverified.
- **`content_hash(channel,m,t,z)` "cheap, per-plane source hash"** — for ND2 you cannot hash pixel content without reading the 85 MB plane, which defeats "no Dataset materialized for lookup." The cheap key must be a *proxy* (file id + offset + mtime + params), not a content hash. This conflation recurs in D ("blake3 over raw tile bytes" as the *durable lookup* key — but tile bytes only exist *after* compute).
- **Recipe-hash vs output-fingerprint** are used interchangeably. Lookup wants recipe-hash (cheap, pre-materialization); Salsa cutoff/backdating and checkpoint dedup *require* an output fingerprint (materialization). D flags cutoff cost as open but the memo key sketch still muddles the two — this needs to be two distinct hashes with distinct lifecycles.
- **Tile-size defaults** (256² / 64³ in A; 512² in D's sketch) are asserted as recommendations while simultaneously listed as un-benchmarked open questions.
- **cc3d "the perf upgrade"** — after your own correction (~1.3–1.4× single-call, not orders of magnitude), calling it *the* perf upgrade for the default single-labeling path overstates it.
- **Clipmap "~90 fps / 20 B samples / 355 MB"** is a 2005 GPU-Gems terrain figure; decorative, not evidence for a microscopy viewer.

## 3. Contradictions between sections

- **Is a single frame tiled at all?** A's entire premise is "6554² frames never materialize whole." C's scope correction says a frame is *only 85 MB, fits one texture, tiling is justified by 5D not frame size.* These are in direct tension and unreconciled — and it's load-bearing (see §5).
- **Tile size:** 256² (A) vs 512² (D sketch) vs "maybe none for 2D" (C). Three answers.
- **First-cut backing store:** on-the-fly dask/zarr coarsen (A) vs OME-Zarr/NGFF on disk (C) vs memmap-first (D). Three different day-one substrates.
- **Structure-domain canonical layout:** flat 1D CSR LabelLayer (B) vs RLE runs + union-find (A) vs Arrow/numpy columnar tables **explicitly not routed through tiles** (D). The user gets a different "canonical" per section.
- **Are structure domains tiled?** A/B tile them (per-brick CCL, `tile_key` on `LabelLayer`, border-merge). D says represent Label/Point/Track as whole columnar tables and *do not route through the tile path.* Genuine architectural fork with opposite memo-granularity consequences.
- **ND2 sub-frame access:** A states nd2 is per-frame-only so sub-frame ROI *requires transcode to Zarr first.* C says the provider's "main path" is built on nd2's lazy/dask interface. You cannot serve a 256² sub-frame tile from nd2 without reading the whole frame — so either transcode (A) or read-whole-then-tile-in-RAM (implied by C's 85 MB point). Unresolved.

## 4. Integration risks vs the locked design

- **Implicit-sharing CoW vs identity-based invalidation (internal to D).** D proposes in-place mutation via `values_for_write()` when refcount==1 *and* "object identity = free upstream-change signal." A layer mutated in place keeps its identity but changes content → identity-based memo will **not invalidate downstream**. Silent stale-hit bug baked into the recommendation.
- **Track identity vs tile-local CCL.** Track is a locked domain requiring stable ids over the Timepoint axis, but tile-local CCL + border-merge renumbers, and a region spanning tiles isn't finalized until all spanning tiles are pulled. This **breaks demand-driven partial evaluation for the Track/Label domains specifically** — you can't promise a label id before its whole region is realized. Flagged as an open Q but it's closer to a design contradiction with "lazy pull."
- **Lattice transfers don't all tile cleanly.** `coarsen=reduce` across Plane→Frame→…→Global reduces over z,y,x; a reduction crossing tile borders needs a **tree-reduce / halo**, not independent tiles. "Same math, now tile-wise" understates this — refine=broadcast tiles trivially, reduce does not.
- **Hidden calibration reads → silent stale memo.** Memo key includes "calibration subset read," but with 10 domains whose transfers pull pixel_size/optics metadata, determining that subset requires static declaration or dynamic tracking. Any missed read = silent corruption. This is the highest-probability correctness landmine and deserves a *mechanism* (declared reads / tracked context), not a caveat.
- **Field layer vs tile memo.** The value/field socket layer's "evaluate only where consumed" granularity is never reconciled with tile-granular memo — risk of double-caching or key collisions between field-expression memo and tile memo.

## 5. Single highest-leverage next decision

**Settle the provider's atomic read granularity — whole-frame-at-85 MB vs sub-frame tile — with one benchmark, before writing `provider.py`.** It is the keystone because it resolves the A↔C contradiction and cascades into every open fork:
- If **frame-atomic** (accept C's 85 MB reality): no ND2→Zarr transcode needed, no sub-frame streaming for 2D, "selective full-res ROI" collapses to trivial, tiling becomes purely a **5D/memo-key** concern, and much of A's substrate complexity evaporates.
- If **sub-frame-tiled**: ND2 *must* be transcoded to a tiled store, tile size must be chosen, border-merge/halo machinery is mandatory.

Everything else (tile size, structure-domain tiling, memo-key shape, whether Track can be lazy) is downstream of this one measurement. Benchmark a tiled `QGraphicsScene` (or QRhiWidget) reading whole 6554² frames + coarsen-in-RAM against a sub-frame Zarr path, across a real 5D stack — then commit. Do not design two contradictory substrates around an unmeasured assumption.

  (read/memo vs display vs compute): a frame is tiled at the storage/memo layer and atomic only as a
  transient viewer buffer; tile = 512² ≡ the b2nd block (config; benchmark default); day-one store =
  b2nd; structure domains are Arrow tables computed whole-frame and *sliced* (not recomputed) per
  display tile.
- **Concrete correctness mechanisms (§I)** unified by one invariant — *memo identity is a cheap
  monotonic `revision` + declared inputs, never Python `id()`, never an 85 MB content read*: two-hash
  memo, a `revision` stamp + frozen `writeable` on `AttributeLayer`, `Granularity.WHOLE_FRAME` for
  connectivity, associative-monoid tree-reduce (`mean` carries `(sum,count)`), a recording
  `ReadContext` for calibration, and a disjoint FIELD memo namespace with `VirtualArray` for
  constant/broadcast fields.

## Two NEW blocking issues the §J critic surfaced — settle before implementing

1. **The Channel axis is addressed inconsistently.** §G/§H write `get_tile(m,t,z,c,…)` and
   `plane_index (m,t,z,c)`, but Phase-1 [domains.py](../../nodegraph/domains.py) has
   `AXIS_ORDER = ("m","t","z","y","x")` with **no `c`** (Channel is orthogonal, bridges-only) and
   `AxisSizes.shape_for` has no C dimension. Where Channel lives in the store/tile/memo model — a 6D
   array with a non-lattice C, or one 5D `(M,T,Z,Y,X)` array *per channel* — is **upstream of** the
   b2nd layout, the `get_tile` signature, and every leaf recipe-hash. **Decide this first.**
2. **Restate the "content-hash memo" invariant.** §I.a rightly forbids content-hashing an 85 MB leaf
   plane and makes the lookup key a **proxy**; content-hash is demoted to cutoff/dedup. So V2.00 §9's
   "content-hash memoization" wording should become *proxy-lookup index + content-fingerprint for

Other §J catches to honor at implementation time: QRhi's OpenGL/GLES fallback caps textures at
**2048–4096** (6554 > 4096 → needs a runtime `maxTextureSize()` tiling check, not "fits one texture");
`cc3d 0.27 s / 512³` does not transfer to a 6554² anisotropic plane (compute-once affordability is
**assumed** — benchmark it); freezing `AttributeLayer.values.flags.writeable` on a `np.asarray` result
is an **aliasing footgun** (copy-or-view-then-freeze); and `reducers.first` **is** tile-reducible
(don't force it to whole-frame).

## G. Second pass — filling the missing-routes gaps

This pass targets the routes the V2.01 addendum left thin: a native full-resolution ROI store, a real cancellation/prefetch engine, a cross-platform GPU viewer, the Point→Label connectivity bridge, and the barely-served MEASUREMENTS/VALUE-FIELD layers. **Two additions dominate and should be adopted now.** First, **Blosc2 NDim (b2nd)** — its double partitioning (multidim chunks sized to L3, split into blocks sized to L1/L2, where the *block* is the unit of decompression) gives native full-resolution sub-region ROI reads that never materialize an 85 MB frame, and with no Zarr ingest step ([Introducing Blosc2 NDim](https://blosc.org/posts/blosc2-ndim-intro/)). Neither *replaces* the V2.01 picks; both slot in underneath them.

One caveat carried from verification applies throughout: b2nd gives fast full-res ROI but has **no** multiresolution/MIP layer — coarse-for-viewing remains cluster C's job (a separate pyramid or a TensorStore `downsample()` view).

## H. Resolving the cross-section contradictions

The six contradictions the critic flagged are not genuine disagreements about one thing — each is two clusters describing **different layers of the stack** (storage read vs. GPU display vs. memo key vs. compute) and asserting a stance that is only true at its own layer. Below, each is resolved by naming the layer each claim owns, then picking the layout that the locked design's content-hash memo + lazy PULL contract actually requires. The recurring principle: **the read/cache/memo layer is tiled and block-granular; the display layer may treat a single in-view plane as atomic; and the structure-computation layer is whole-domain and off the tile path.**

### H.1 Is a single 85 MB frame tiled at all? (A: never materialize — C: fits one texture)

Both are correct because they describe different layers, and the b2nd storage decision dissolves the conflict. On the **read/pull path**, a frame is never materialized whole: an `.b2nd` array is double-partitioned into chunks and blocks where "the block is the unit of decompression," and "slicing an NDArray decompresses only the blocks that the slice touches" ([Blosc2 NDim intro](https://blosc.org/posts/blosc2-ndim-intro/), [python-blosc2 NDArray docs](https://www.blosc.org/python-blosc2/getting_started/tutorials/01.ndarray-basics.html)) — so a `get_tile(m,t,z,c,y0:y1,x0:x1)` pull touches only the intersecting blocks and the 85 MB plane is never assembled in RAM to serve a tile. On the **display path**, a 6554×6554 plane sits comfortably in RAM (85.9 MB) and inside a single GPU texture (well under the 16384 max-dimension of every QRhi backend — [QRhiWidget](https://doc.qt.io/qt-6/qrhiwidget.html)), so C's "one texture" fast-path for the single focused plane is a legitimate viewer optimization. A (tiled) governs storage/memo; C (atomic) governs display of one in-view plane only. **Single confirming measurement:** on a real 6554² uint16 frame, compare single-tile b2nd ROI decompress latency against whole-plane decompress latency — if the ROI read is a small fraction of the whole-plane read, block-granular pulling is justified over "decode the plane then slice." **Memo/pull consequence:** the memoized unit on the read path is the tile/block (keyed `recipe_hash + tile_id`); the whole-plane texture is an ephemeral viewer-side buffer, never a memo entry, so it cannot become a stale-hit source.

**Decision: A frame is tiled at the storage/read/memo layer (b2nd block-granular ROI, never whole-frame materialization on pull); "one plane = one texture" survives only as a viewer-side display fast-path for the single in-view plane, not as a memoized payload.**

### H.2 Tile size: 256 vs 512 vs none

"None" (whole-frame) is rejected outright on eval grounds: a monolithic full-frame decode has no interior checkpoint, and Python cannot preempt a running thread ([CPython #107505](https://github.com/python/cpython/issues/107505)), so an un-tiled pull is uncancellable during a fast T/Z scrub — the tile boundary *is* the cancellation checkpoint and the prefetch/backpressure quantum. Between 256 and 512, the deciding constraint is that the tile should equal the b2nd **block** (the unit of decompression) so a tile pull hits whole blocks with no partial-block waste, with the chunk a small multiple of the block ([PyTables b2nd slicing](http://blosc.org/posts/pytables-b2nd-slicing/)). 512×512 uint16 = 512 KB/tile sits in the L2-scale range the block partition targets, amortizes decompress setup better than 256, and yields ~4× fewer QGraphicsItems in the scene than 256; 256 buys finer cancellation/prefetch granularity and lower per-tile latency at the cost of more scheduler traffic. Default to **512×512, block-aligned, and expose it as config** — the research is explicit that tile-size defaults are un-benchmarked and must not be asserted. **Single confirming measurement:** sweep {256, 512, 1024} tile/block sizes on real frames measuring both single-tile ROI decompress latency and end-to-end scrub frame-time, and take the knee. **Memo/pull consequence:** tile size is simultaneously the memo-key granularity, the cancellation checkpoint interval, and the prefetch unit — one number sets all three, so it must be a benchmarked config value, not three independent constants.

**Decision: Default tile = 512×512, defined as the b2nd block size (chunk = small multiple), config-overridable; reject "none" because an un-tiled pull is uncancellable and defeats prefetch/backpressure. Treat 512 as a benchmark default, not a fixed constant.**

### H.3 Day-one store: dask/zarr vs OME-Zarr vs memmap

The day-one store is **Blosc2 `.b2nd` on disk**, with ND2 ingested once. b2nd is the only option that gives native full-resolution sub-block ROI reads *without a Zarr ingest step*, is numpy-native with SIMD wheels, and needs no Bazel/build ([Blosc2 NDim intro](https://blosc.org/posts/blosc2-ndim-intro/)). Raw `memmap` is rejected because it offers no compression (5D at 85 MB/plane is enormous) and no block-level ROI decompression — every sub-frame read faults in whole pages. dask/zarr and OME-Zarr are rejected for day one because they impose an ingest + chunk-transcode and a heavier ecosystem for a benefit (cloud/object-store concurrency, multiscale conventions) the desktop app does not yet need; they remain the documented "later" option behind the same `get_tile` contract. TensorStore (async cache + virtual `downsample()` view — [TensorStore](https://google.github.io/tensorstore/), [tensorstore.downsample](https://google.github.io/tensorstore/python/api/tensorstore.downsample-store.html)) is deferred to the scheduler/coarse-view role, not adopted as the raw store, since using it means re-entering the Zarr world and it is "not an officially supported Google product." **Single confirming measurement:** on a real ND2, measure one-time ingest→b2nd cost, single-tile ROI decompress latency, and on-disk size for b2nd vs. memmap vs. zarr3+Blosc — b2nd should win ROI latency at a compression ratio comparable to zarr3+Blosc and far below memmap's footprint. **Memo/pull consequence:** memo keys reference a b2nd array id + region proxy; because the store sits behind `get_tile`, the day-one choice is swappable to zarr3/TensorStore later without touching the pull contract or the memo keys.

**Decision: Day-one store = Blosc2 b2nd (ingest ND2 once), not memmap, not dask/zarr/OME-Zarr. Zarr3/OME-Zarr and TensorStore stay behind the `get_tile` contract as the deferred scale-out / async-scheduler path.**

### H.4 Structure-domain canonical layout: CSR flat (B) vs RLE+union-find (A) vs Arrow columnar (D)

These three describe different *kinds* of structure data and only one is a canonical wire layout. The canonical layout for the per-element structure domains (Label, Point, Track) is **Arrow columnar (D)**: immutable RecordBatch buffers are exactly what content-hash memo wants — adding a measurement column produces a new buffer and a new hash, so an identity-based cache cannot silently serve a stale table (directly closing the CoW stale-hit risk), and Arrow's zero-copy IPC/C-Data-Interface handoff lets heavy CCL/regionprops workers return tables without serialization ([Arrow Columnar Format](https://arrow.apache.org/docs/format/Columnar.html), [Arrow IPC](https://arrow.apache.org/docs/cpp/ipc.html)). B's **CSR** is not a competing canonical store — it is the *encoding of the connectivity/topology columns* (Point/Track edges, ragged Track-over-Timepoint), which Arrow expresses natively as `ListArray` offsets+values, so CSR lives *inside* the Arrow table rather than beside it. A's **RLE + union-find** is demoted to a transient implementation detail of the CCL producer (how a label mask is computed and merged), never a payload on a wire or a memo key. Because these tables are KB–low-MB (thousands of elements × tens of columns), a *full* content hash over the contiguous buffers is genuinely cheap — the 85 MB proxy-key problem does **not** apply to structure domains. **Single confirming measurement:** hash a realistic structure table (few-thousand labels × tens of columns) to confirm sub-millisecond full-hash cost, and confirm an Arrow `ListArray` round-trips CSR connectivity (offsets+indices) without a copy. **Memo/pull consequence:** structure-domain memo is a cheap *full* content hash of the whole immutable table — a genuinely different, and simpler, granularity than the proxy-keyed image tiles.

**Decision: Arrow columnar (immutable RecordBatch) is the canonical structure-domain layout; CSR connectivity lives as Arrow `ListArray`/offset columns within it; RLE+union-find is an internal CCL compute detail, never canonical. Structure tables use cheap full content-hash keys, not proxies.**

### H.5 Are structure domains tiled (A/B) or off the tile path (D)

Structure domains are **off the tile path (D)** — computed and memoized at whole-domain (Plane/Frame) granularity, never as tile providers. The connectivity research is decisive that both CCL and watershed are *global* operations: a basin or component can span the entire frame, so tile-independent execution requires halos plus a border union-find reconciliation and, worse, renumbers components per tile — which breaks the Track/Label id-stability the critic flagged as an integration risk ([cuCIM #89, watershed is heap-based/global](https://github.com/rapidsai/cucim/issues/89)). This is also the concrete lazyflow hazard: correctness that depends on each operator's hand-written ROI dirty-map silently serves stale regions for non-local kernels ([lazyflow propagateDirty](https://ilastik.github.io/lazyflow/operator_overview.html)), which is exactly why non-local structure ops must not be tiled. The finished **label raster** (a Voxel-domain image) may be tiled *downstream for display and for raster-consuming nodes*, but it is *produced whole and atomically*; the per-element attribute tables (H.4) are never tiled at all. Whole-frame CCL is affordable to run once and cache — cc3d labels a 512³ single-label volume in 0.27 s ([cc3d benchmarks](https://seunglab.org/connected-components-3d/benchmarks/)) — so memoize-once is viable. **Single confirming measurement:** time whole-frame cc3d/`label` and marker watershed on a real 6554² plane to confirm the one-time cost fits an acceptable "compute-once, cache" budget (sub-second to low-seconds); no tiling measurement is needed because the stance is a correctness argument, not a performance trade. **Memo/pull consequence:** structure memo has two granularities — the whole label *raster* is one payload keyed on a **proxy** recipe-hash (85 MB, too large for content hash), while the small attribute *tables* use cheap full hashes; the lazy pull realizes the structure once per (Plane/Frame, recipe) and then serves display tiles from the cached raster, so id stability comes from id-carrying watershed seeds, not from any tile-local renumber.

**Decision: Structure domains are off the tile path — CCL/watershed run whole-domain (Plane/Frame) and are memoized once; the resulting label raster may be tiled only for downstream display, and per-element attribute tables are never tiled. Tile-local structure computation is prohibited to preserve Track/Label id stability.**

### H.6 ND2 sub-frame access: requires transcode (A) vs read-whole-then-tile (C)

Resolved by a one-time ingest boundary: **transcode ND2 → b2nd once, after which sub-frame access is native (A is right for the steady state); direct ND2 read-whole-then-tile (C) survives only as the pre-ingest live-preview fallback.** ND2 is not a native driver for either b2nd or TensorStore, so there is no free arbitrary sub-frame read from the source container; the storage research confirms the resolution is "transcode ONCE at ingest, then true sub-frame access," and C's read-whole-then-tile "only applies if reading directly from ND2 without an ingest step." Once ingested to b2nd, sub-frame ROI reads are block-native and cheap ([Blosc2 NDim intro](https://blosc.org/posts/blosc2-ndim-intro/)); before ingest, a live preview must decode a whole plane and cache it at plane granularity. **Single confirming measurement:** benchmark nd2/bioio *direct* sub-frame read latency against b2nd ROI read *after* ingest, plus the one-time per-volume ingest cost — if ND2 direct sub-frame read is no cheaper than a whole-plane read (i.e. the container offers no real sub-frame locality), the transcode-once decision is justified. **Memo/pull consequence:** ingest is a one-time boundary in the pull graph; after it, pull and memo operate on b2nd regions (tile-granular, proxy-keyed); before it, the pull degrades to whole-plane decode memoized at plane granularity, so the preview path and the working path have distinct, non-conflicting memo granularities.

**Decision: Transcode ND2 → b2nd once at ingest; steady-state sub-frame access is native block-granular (A). Direct read-whole-then-tile from ND2 (C) is retained only as the pre-ingest live-preview fallback, memoized at plane granularity.**

## I. Correctness mechanisms (closing the landmines)

These six mechanisms are the enforceable rules that turn the Phase-1 core (`nodegraph/dataset.py`, `nodegraph/transfer.py`, `nodegraph/reducers.py`) into a lazy PULL engine that cannot silently serve stale or inconsistent data. Every one of them is grounded in an existing symbol; the Phase-2 engine (`nodegraph/engine.py`, not yet written) is where the memo table, the pull scheduler, and the `ReadContext` live.

A single primitive underlies (a), (b), (e), and (f): a **monotonic revision stamp** that is cheap to compute and never requires touching pixels. Establish it once:

```python
# nodegraph/revision.py  (Phase-2)
import itertools
_REV = itertools.count(1)
def next_revision() -> int:      # process-monotonic; the memo identity, never id()
    return next(_REV)
```

### (a) Two-hash memo: proxy recipe-hash (lookup) vs output-fingerprint (cutoff/dedup)

The critic correctly separated two things the V2.01 draft conflated. They serve different jobs and have different lifecycles, and **neither may read 85 MB to be computed**.

**recipe_hash** — the *lookup* key, computed *before* compute, purely from structure. For a leaf voxel-read node it is a **proxy** over source identity, never the decoded plane (the storage cluster's finding: `content_hash(channel,m,t,z)` needs an 85 MB decompress, so it cannot be the key). This is exactly Halide's `memoize_tag`: compute one thing but key the cache on a cheap surrogate expression, and Salsa's revision-as-fence.

```python
# leaf read: identity is (file, byte range, mtime, addressing, params) — no pixels
def recipe_hash_of_read(src) -> bytes:
    return blake3(canonical_bytes(
        src.file_id, src.byte_offset, src.mtime_ns,
        src.dtype, src.shape, src.plane_index,   # (m,t,z,c)
        src.reader_params)).digest()

# interior node: op + params + declared reads (e) + UPSTREAM recipe_hashes
def recipe_hash_of_node(spec, params, read_set, upstream_hashes) -> bytes:
    return blake3(canonical_bytes(
        spec.op_key, params, sorted(read_set), tuple(upstream_hashes))).digest()
```

**output_fingerprint** — the *content* hash of the actually-produced payload, computed *after* compute. For lattice attributes it hashes the numpy buffer (`layer.values.tobytes()` via xxhash/blake3); for a tile it hashes only that tile's bytes. Its jobs are **cutoff** and **dedup**, not lookup:

- **Cutoff (backdating).** A node recomputes, but if its new `output_fingerprint` equals the one stored last revision, downstream nodes keyed on that fingerprint *early-out* — the classic Salsa "the input changed but the value didn't" short-circuit. This is why the two hashes must stay distinct: recipe_hash changed (an upstream param moved), but output_fingerprint proves the bytes are identical, so the expensive downstream subtree is skipped.
- **Dedup.** Two *different* recipes (e.g. two reduction orders) that yield byte-identical output share one stored payload, keyed by fingerprint in a content-addressed blob store.

Lifecycle in the pull:

```
pull(node):
  rh = recipe_hash_of_node(...)              # cheap, proxy, no pixels
  if rh in memo:  return memo[rh].payload     # LOOKUP hit
  payload = compute(node)                      # runs kernel
  fp = output_fingerprint(payload)             # CONTENT hash, post-compute
  if fp == memo.prev_fp(node):  mark_backdated(node)   # CUTOFF: downstream may reuse
  memo[rh] = Entry(payload=blob[fp], fp=fp, revision=next_revision())
  return payload
```

`blob[fp]` is the dedup store; `memo[rh]` is the lookup index pointing into it. Blosc2's `vlmeta` metalayer is the natural home for a per-chunk digest so even the leaf proxy can be strengthened without a decode (blosc.org NDim intro).

**Mechanism:** Key the memo *index* on a cheap **recipe_hash** — a proxy over `(file_id, offset, mtime, dtype, shape, plane_index, params)` for leaves and `(op_key, params, declared-reads, upstream recipe_hashes)` for interior nodes, never over pixels — and key a separate content-addressed *blob store* on an **output_fingerprint** hashed from the produced buffer *after* compute; use fingerprint equality across revisions as the backdating cutoff that lets downstream subtrees early-out, and as the dedup key. (Halide `memoize_tag` proxy-key: halide-lang.org/docs/_memoization_8h.html; Salsa backdating/revisions: docs.rs/salsa Durability, github.com/salsa-rs/salsa.)

### (b) CoW identity-invalidation fix: version/epoch stamp

`Dataset` is "immutable-by-convention" and `@dataclass(frozen=True)` — but frozen only forbids *rebinding the field*, not mutating the ndarray it points to. `layer.values[10, 20] = 5` succeeds on a frozen `AttributeLayer`, keeping Python `id()` identical while changing content. An identity-based memo (or any cache keyed on object identity) then serves the pre-mutation result: the critic's silent stale-hit.

Two-part fix. First, make the buffer *actually* immutable so accidental CoW mutation fails loudly instead of silently:

```python
# nodegraph/dataset.py — AttributeLayer
@dataclass(frozen=True)
class AttributeLayer:
    domain: Domain
    name: str
    values: np.ndarray
    layer: Optional[str] = None
    revision: int = field(default_factory=next_revision)   # NEW: content identity

    def __post_init__(self):
        object.__setattr__(self, "values", np.asarray(self.values))
        self.values.flags.writeable = False   # in-place mutation now raises
```

Second, memo identity is the **revision stamp**, never `id()`. Any legitimate derivation allocates a fresh revision; a node that wants CoW-style mutation must route through an explicit `mutate()` that returns a *new* layer with a *new* revision (reusing the buffer only when it can prove no change):

```python
def mutate(self, new_values) -> "AttributeLayer":
    return replace(self, values=new_values, revision=next_revision())
```

`Dataset.with_attribute` already does structural sharing via `replace`; the new layer it stores carries a fresh revision, so any recipe_hash that referenced the old layer's revision (see (a) and (f)) no longer matches → automatic invalidation even though the enclosing `Dataset` shares 99% of its store. This is Salsa's revision model and Arrow's immutable-buffer discipline (a new column = a new buffer = a new hash) applied to `AttributeLayer`.

**Mechanism:** Give every `AttributeLayer` a monotonic `revision` stamp set at construction, freeze `values.flags.writeable = False` so in-place CoW mutation raises rather than silently succeeding, and make all downstream memo keys reference the **revision**, never Python `id()`; a genuine mutation goes through `mutate()` which mints a new revision, so changed content always invalidates. (Salsa revisions: github.com/salsa-rs/salsa; Arrow immutable columnar buffers: arrow.apache.org/docs/format/Columnar.html.)

### (c) Track/Label lazy-pull under tile border-merge

**What breaks.** CCL (`cc3d`, `cucim.skimage.measure.label`) and watershed are intrinsically *global*: one connected component or one flooded basin can span the whole 6554×6554 frame. If you label tile-by-tile as a lazy provider, (1) ids are tile-local and must be renumbered, (2) a border-merge union-find renumbers *again* when neighbor tiles resolve, and (3) a `Track` id that must be stable across the Timepoint domain is destroyed by that renumbering — breaking lazy partial eval for Track/Label. cuCIM has **no** GPU watershed (issue #89), so a seeded bridge can't even be moved off-CPU to brute-force it.

Three candidate rules were on the table: **(A) provisional/deferred ids + finalize-on-full-region**, **(B) force full-region realization**, **(C) tile-local label + union-find border reconciliation**. Provisional ids (A) are rejected: a viewer tile pulled before its neighbors resolve returns ids that *change* on finalize, so any memo entry or Track match keyed on those ids is retroactively wrong — the same silent-stale class as (b). (C) reintroduces the renumber that kills Track stability.

**Chosen rule (B, structured).** Structure-domain producers are **whole-domain (Plane/Frame) nodes, off the tile path**. The connectivity node declares its granularity; the engine realizes the *entire* frame once and memoizes the whole label array as one payload keyed by a proxy recipe_hash (per (a) — never the 85 MB content). Tiling is a purely *downstream, read-only* concern: the viewer's `get_tile` on a `LABEL` layer **slices the finished array** (a numpy view, zero recompute), it never invokes CCL per tile.

```python
# Phase-2 node metadata
class Granularity(Enum):
    TILEABLE   = "tileable"     # image ops that honor the tile provider
    WHOLE_FRAME = "whole_frame" # CCL / watershed / any global connectivity op

# engine: a WHOLE_FRAME node is realized in full and memoized as one payload
if spec.granularity is Granularity.WHOLE_FRAME:
    label_arr = compute_full(node)                 # cc3d / skimage.watershed
    ds = ds.with_layer(Domain.LABEL, name, label_arr, layer=src_layer)
# downstream viewer tile is just a slice — no CCL, ids already global & stable
def get_label_tile(layer, y0, y1, x0, x1):
    return layer.values[..., y0:y1, x0:x1]         # view, cheap
```

**Track id stability** then comes not from CCL (whose ids are arbitrary and unstable across t) but from **seeded watershed**: rasterize tracked-point ids into `skimage.segmentation.watershed(-edt, markers=point_ids, mask=fg)` so each output label id *is* the seed's id, carried through unchanged frame-to-frame. The seed ids are the stable Track identity; no tile-local renumber ever occurs.

**Mechanism:** Mark connectivity producers (CCL, watershed) `Granularity.WHOLE_FRAME` — realize the full label/track array once, memoize it as a single proxy-keyed payload, and forbid per-tile CCL; the viewer's `get_tile` only *slices* the finished array. Achieve Track/Label id stability by using id-carrying seeded watershed (tracked-point ids as `markers`) rather than renumber-prone CCL, so ids are global and stable across Timepoint by construction. (No GPU watershed: github.com/rapidsai/cucim/issues/89; seeded markers semantics: scikit-image.org watershed API; exact anisotropic EDT: github.com/seung-lab/euclidean-distance-transform-3d.)

### (d) Tree-reduce / halo for lattice coarsen=reduce across tile borders

`transfer.py::_apply_lattice_step` computes a lattice `reduce` by folding whole axes (`_reduce(values, pos, reducer)`). When the source array is delivered by a *tile* provider rather than materialized, a Voxel→Frame reduce (fold over `z,y,x`) cannot be computed as independent per-tile reductions naively concatenated — a global `mean` needs partial *sums and counts*, not per-tile means. The fix is to express each reducer as an **associative monoid** `(lift, combine, lower)` and fold tiles up a reduction tree.

```python
# nodegraph/reducers.py — add a partial-aggregate protocol
class PartialReducer(Protocol):
    associative: bool
    def lift(self, a, axis) -> Any: ...     # tile -> partial
    def combine(self, p, q) -> Any: ...     # partial ⊕ partial  (associative)
    def lower(self, p) -> np.ndarray: ...   # partial -> final array

MEAN = PartialReducer(associative=True,
    lift   = lambda a, ax: (np.nansum(a, ax), np.sum(~np.isnan(a), ax)),
    combine= lambda p, q: (p[0]+q[0], p[1]+q[1]),
    lower  = lambda p: p[0] / p[1])
SUM = ...(lift=nansum, combine=add, lower=identity)      # already associative
MAX = ...(lift=nanmax, combine=maximum, lower=identity)  # idempotent monoid
COUNT = ...(lift=count, combine=add, lower=identity)
MEDIAN = FIRST = PartialReducer(associative=False, ...)  # NOT tile-reducible
```

Tree-reduce path: each tile computes `lift` over its interior; partials combine pairwise (`combine`) up a balanced tree; only the small coarse result is memoized per partial (cheap — the reduced shape, not the tile). This also fixes the T/Z-scrub cancellation budget: a cancelled pull drops its partial without corrupting the fold.

**Halo vs no-halo — the key distinction.** A *pure lattice axis-fold* (what `transfer.py` does) needs **no halo**: it aggregates *over* an axis, and the monoid tree handles border tiles associatively. A **halo (ghost border of width = kernel radius)** is needed only for *stencil/neighborhood* ops — a gradient, an EDT, a morphological op — that a downstream field or watershed consumes; those pull a ring of neighbor-tile pixels before computing. Non-associative reducers (`median`, `first`) fall back to `Granularity.WHOLE_FRAME` (per (c)) because they cannot be tree-reduced at all.

```python
def execute_tiled_reduce(tile_provider, step: LatticeStep, pr: PartialReducer):
    if not pr.associative:
        raise NonTileable(step)                 # force whole-axis realization
    partials = (pr.lift(t.values, step.axes) for t in tile_provider.interior_tiles())
    return pr.lower(functools.reduce(pr.combine, partials))   # tree-reduce
```

**Mechanism:** Rewrite lattice `reduce` steps as associative monoids `(lift, combine, lower)` — `mean` carries `(sum, count)` partials, `sum/max/min/count` self-combine — and tree-reduce tile partials so a coarsen across tile borders is exact and cancellation-safe; pure axis-folds need **no** halo, only stencil/neighborhood ops pull a radius-wide ghost halo from neighbor tiles, and non-associative reducers (`median`, `first`) drop to `WHOLE_FRAME` realization. (Frontier-buffered partial aggregation: cacm.acm.org timely-dataflow.)

### (e) Declared-reads: calibration/optics metadata enters the memo key

The `Dataset.metadata` dict drives "metadata-intelligent params." If a node reads `metadata['pixel_size_um']` or an optics field directly, that read is *invisible* to `recipe_hash_of_node` (a) — so if calibration changes, the recipe hash is unchanged and the memo serves a stale result. This is exactly lazyflow's `propagateDirty` under-reporting hazard: correctness distributed across every operator, and the strongest argument that reads must be *recorded automatically*, not hand-declared.

Mechanism: nodes never touch `metadata` directly; every read goes through a recording `ReadContext`, and the recorded `(key, value_digest)` set folds into that node's recipe_hash — declared reads become automatic tracked edges, Adapton/Salsa-style.

```python
# nodegraph/engine.py
class ReadContext:
    def __init__(self, meta): self._meta = meta; self.reads = {}
    def meta(self, key):
        v = self._meta[key]; self.reads[key] = blake3(canonical_bytes(v)).digest()
        return v
    calib = meta   # same recording path for optics/calibration

# compute wrapper
def compute(node, ds):
    ctx = ReadContext(ds.metadata)
    payload = node.run(ds, ctx)                 # node calls ctx.meta('pixel_size_um')
    node.recipe_hash = recipe_hash_of_node(node.spec, node.params,
                                            ctx.reads, upstream_hashes)  # reads folded in
    return payload
```

Defense in depth: wrap `Dataset.metadata` in a Mapping proxy that raises on `__getitem__` outside a `ReadContext` (or a debug-mode guard), so a hidden read is a hard error in test rather than a silent stale-hit in production. Any change to a read key changes its digest → changes recipe_hash → invalidates precisely the nodes that read it, and nothing else.

**Mechanism:** Route all metadata/calibration/optics access through a recording `ReadContext` whose `(key, value_digest)` read-set is folded into the node's recipe_hash, and guard `Dataset.metadata` against un-contexted reads so hidden calibration reads become tracked memo dependencies (automatic declared-reads), not silent stale hits. (Automatic dependency tracking: cs.tufts.edu Adapton, github.com/salsa-rs/salsa; the under-reported-dirty cautionary case: ilastik.github.io/lazyflow operator_overview propagateDirty.)

### (f) Reconciling field-expression memo vs tile-granular memo

A VALUE/FIELD socket (`sockets.py`: `is_field`, `SocketSpec.domain`) carries an *unevaluated* expression tree, Blender-style, realized lazily only where a consumer binds it to a domain. The unreconciled hazard: the same field could be materialized at *tile* granularity (image-coupled) and at *element* granularity (on Label/Point/Track), double-caching and colliding keys with the image tile memo.

Reconcile with Halide's `compute_at` discipline: **one materialization site per field**, chosen by the consumer, keyed in a **disjoint FIELD namespace**.

```python
@dataclass(frozen=True)
class Field:                       # the unevaluated expression tree
    op: str
    inputs: Tuple["Field", ...] = ()
    reads: Tuple[LayerKey, ...] = ()      # AttributeLayer keys this leaf reads

def field_expr_hash(f: Field, ds: Dataset) -> bytes:
    # structure + referenced layer REVISIONS (b) + declared reads (e)
    leaf_revs = tuple(ds.attributes[k].revision for k in f.reads)
    return blake3(canonical_bytes(f.op, tuple(field_expr_hash(i, ds) for i in f.inputs),
                                  f.reads, leaf_revs)).digest()

def realize(f, domain, ds, *, tile=None):
    if tile is not None:                          # image-coupled → borrow tile granularity
        key = ("field", field_expr_hash(f, ds), domain, tile.id)      # FIELD namespace
    else:                                         # element domain → one site per domain-version
        key = ("field", field_expr_hash(f, ds), domain, domain_version(ds, domain))
    if key in memo: return memo[key]
    out = eval_field(f, domain, ds, tile)         # constant/broadcast → VirtualArray, no materialize
    memo[key] = out
    return out
```

Key facts that make it collision-free: the FIELD cache key `("field", field_expr_hash, domain, token)` lives in a namespace disjoint from the IMAGE tile key `(recipe_hash, tile_id)`; `token` is `tile.id` for image-coupled fields and a `domain_version` for element-domain fields (Label/Point/Track are **never** tiled — consistent with (c)); and `field_expr_hash` reuses the exact same **revision** stamps from (b) and the **declared reads** from (e), so field invalidation is automatic. Constant/broadcast fields realize to a `VirtualArray` and never materialize at all (Blender's GVArray), so an unused field costs nothing — matching the lazy PULL model.

**Mechanism:** Carry fields as unevaluated expression trees and give each exactly one materialization site chosen by its consumer, keyed `("field", field_expr_hash, domain, token)` in a FIELD namespace disjoint from the image tile namespace — `token = tile_id` for image-coupled fields, `domain_version` for element-domain fields (structure domains never tiled) — where `field_expr_hash` is built from the tree structure plus referenced-layer **revisions** (b) plus **declared reads** (e); constant/broadcast fields realize to a non-materializing `VirtualArray`. (Halide `compute_at`/single-site scheduling: people.csail.mit.edu/jrk/halide-pldi13.pdf; field expression trees + GVArray virtual realization: code.blender.org/2021/08/attributes-and-fields.)

---

**Cross-cutting invariant.** (a)'s revision-proxy fence, (b)'s stamp, (e)'s recorded reads, and (f)'s field hash are the *same* mechanism at four scales: memo identity is always a cheap monotonic revision + declared inputs, **never** Python `id()` and **never** an 85 MB content read. Consistency (glitch-freedom, the stale-hit classes) is a global invariant of that fence, not a per-operator duty — the lazyflow lesson made structural.

### Remaining unverified claims (not self-flagged)

- **"a 6554² plane fits inside a single GPU texture, well under the 16384 max-dimension of every QRhi backend" (H.1).** False as stated. D3D11/Metal/Vulkan guarantee ≥16384, but QRhi's **OpenGL/GLES fallback** (the "elsewhere" path QRhiWidget advertises) guarantees only **2048–4096** (`GL_MAX_TEXTURE_SIZE` floor). 6554 > 4096, so the "one plane = one texture" display fast-path silently breaks on the exact low-end/GL path QRhi exists to cover. Needs its own runtime `maxTextureSize()` check, not an assertion.
- **cc3d "0.27 s for 512³" → sub-second on 6554² (H.5, I.c).** Cited but not applicable: 512³ isotropic single-label ≠ a 6554×6554 anisotropic 5D plane (~43M vs ~134M elems, different conn/dtype). The doc does ask for a real 6554² timing, so treat the "compute-once is affordable" verdict as **assumed, not shown**.
- **"512 KB/tile sits in the L2-scale range" (H.2).** 512 KB exceeds typical per-core L2 (256 KB–1.25 MB); the block-in-L2 premise for 512² uint16 is shakier than stated. Part of the (already-flagged) sizing sweep, but the L2 justification itself is wrong-ish.
- **">100 GB/s LZ4/BLOSCLZ decompress ⇒ near-free tile pull" (G.1).** That figure is aggregate, multi-core, in-cache, synthetic. Single-tile cold ROI decompress latency (the thing on the scrub path) is nowhere near it. Hedged as "near-free" but the number does not support the per-tile claim.

### Contradictions with the locked v2 design

- **"content-hash memo" invariant vs. proxy recipe_hash (I.a).** The locked v2 is stated to be a *content-hash memo*. Section I.a explicitly forbids content-hashing the leaf (85 MB decompress) and makes the **lookup key a proxy** (`file_id, offset, mtime, params`), demoting content-hash to cutoff/dedup only. This is a genuine **revision** of the locked invariant, not a gap-fill. If the v2 spec literally says "content-hash memo = memo identity," I.a contradicts it and the spec must be restated as *proxy-lookup index + content-fingerprint for cutoff/dedup*, or the invariant is a lie in the leaf case.
- **Channel threaded as an image/tile axis (G.1, G.2, H.1, H.2) vs. `domains.py`.** The code is explicit: `AXIS_ORDER = ("m","t","z","y","x")` — **no `c`** — and Channel is "a standalone axis-domain, orthogonal to the lattice … participates only through explicit bridges." But G/H repeatedly write `get_tile(m,t,z,c,y0:y1,x0:x1)`, priority keys over `(m,t,z,c,x,y,level)`, and `plane_index (m,t,z,c)`. The store shape (`shape_for` → `(M,T,Z,Y,X)`) has no C dimension. So the entire b2nd/tile/memo addressing assumes a lattice axis the locked model says does not exist. Unreconciled.
- **`AttributeLayer.__post_init__` freezing `values.flags.writeable=False` (I.b) is an aliasing footgun.** `with_layer`/`__post_init__` run `np.asarray(values)`, which returns the **caller's** array unchanged when it's already an ndarray. Freezing its `writeable` flag mutates the upstream buffer's flags (and raises if it's a non-owning view). The "immutable buffer" fix as written can freeze arrays the producer still holds, or throw. Needs an explicit copy-or-`.view()`-then-freeze, which then costs the structural-sharing cheapness the design leans on.
- **`reducers.first` treated as non-associative → WHOLE_FRAME (G.4/I.d).** `_first` (take index 0 along axis) *is* resolvable across tiles by position (global-first lives in the first tile); lumping it with `median` as "not tile-reducible" is over-conservative and needlessly forces whole-frame realization. Minor, but it's a real mismatch with the existing reducer semantics.

### Single most important thing still unresolved

**Where does Channel live in the store / tile / memo model?** Every G/H storage, prefetch, and memo-key decision is written against a `c`-carrying addressing that the locked lattice (`AXIS_ORDER`, `shape_for`, "Channel is orthogonal, bridges-only") does not have. Until this is settled you cannot define: the b2nd array rank/layout (is it one 5D `(M,T,Z,Y,X)` array per channel, or a 6D array with a non-lattice C?), the `get_tile` signature, or any leaf `recipe_hash` (which currently hashes a `(m,t,z,c)` plane_index). It is upstream of the tile-size sweep, the ND2→b2nd transcode boundary, and the proxy-key definition — so it blocks the parts of I that are otherwise the strongest. (Runner-up: the **asyncio↔Qt bridge** in G.2 — qasync vs. hand-rolled QThreadPool+epoch-registry — is named as load-bearing for the whole four-layer eval engine but never chosen; the "structured concurrency does not cancel CPU work" caveat means the token layer, not the TaskGroup layer, is doing all the real cancellation, which weakens the case for adopting the asyncio shell at all.)
