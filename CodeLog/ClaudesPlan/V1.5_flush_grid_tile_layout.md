# V1.5 — Flush-grid tile layout

**Date:** 2026-04-30
**Author:** Gabriel Declercq (with Claude)
**Status:** in progress
**Branch:** Version-1.5

## Goal

Make the tile layout always render as a flush grid where each M
position occupies its own (col, row) cell with no per-pixel overlap.

## Background

V1.4 fixed the per-M stage XY metadata read, so we now get one unique
(x, y) per M. But `compute_tile_layout()` still converts those positions
to physical pixels:

```python
px = ((xs - xs.min()) / pixel_size_um).round().astype(int)
canvas_w = int(px.max() + tile_w)
```

If the acquisition has tile overlap — say tile size 400 µm with a step
of 200 µm — then `px` for adjacent columns differs by 400 px while
each tile spans 800 px in the canvas. They overlap by 50%. In the
sidebar tile widget that overlap is large enough that the rectangles
literally stack and the M-index labels pile on top of each other.

The user wants a clean grid: discover the underlying column/row
structure from the stage XY data, assign each M a discrete (col, row),
and lay tiles out flush against each other.

## Approach

### 1) Cluster stage X and stage Y into column / row centroids

Sort the values, sweep through, and start a new cluster whenever the
gap to the previous value exceeds a tolerance. Tolerance is **30 % of
the tile size in µm**:

- Heuristic — fine enough to keep adjacent columns separate even at
  70 % overlap, coarse enough to absorb stage jitter (≤ 10 % of step).
- Per-axis (X tolerance uses tile width × pixel size; Y tolerance uses
  tile height × pixel size — they're typically equal but the math is
  symmetric).

```python
def _cluster_axis(values, tolerance):
    sorted_vals = np.sort(values)
    clusters = []
    current = [sorted_vals[0]]
    for v in sorted_vals[1:]:
        if v - current[-1] <= tolerance:
            current.append(v)
        else:
            clusters.append(float(np.mean(current)))
            current = [v]
    clusters.append(float(np.mean(current)))
    return clusters
```

### 2) Assign each M a `(col_idx, row_idx)`

For each tile's x value, find the closest column centroid; same for y.
Y is reversed so the highest stage Y becomes row 0 (top of image —
microscope stages grow Y upward, image arrays grow Y downward).

### 3) Build the layout

```python
canvas_w = n_cols * tile_w
canvas_h = n_rows * tile_h
offsets[m] = (row_idx[m] * tile_h, col_idx[m] * tile_w)
```

No per-pixel arithmetic, no overlap. The widget's existing
`min(avail.w / canvas_w, avail.h / canvas_h)` letterbox scale handles
"fit to panel": with N×M tile units, the panel fits an N×M grid
exactly.

### 4) Fallbacks

- If stage XY spread is < 0.1 µm in both axes → all tiles look like
  one position → grid fallback (sqrt-row-major).
- If stage XY data is missing (`stage_xy_um == []`) → grid fallback.
- If clustering raises (shouldn't, but defensively) → grid fallback.

The `source` field on `StitchLayout` stays `"stage_xy"` when the
cluster path succeeds, `"grid_fallback"` otherwise — the metadata-table
diagnostic from V1.4 keeps working.

## Key Decisions

1. **Clustering tolerance = 30 % of tile-size in µm.** Tunable in
   one place if specific acquisitions need it.
2. **Same algorithm for preview and stitch.** Keeps the WYSIWYG
   relationship between the sidebar layout and the exported TIFF.
3. **Y axis flipped** so the on-screen layout matches a real
   physical-up orientation.
4. **No "render at physical positions" mode.** Real overlap blending
   would need feathered seams + per-pixel re-projection; for V1.5
   we stick with the discrete grid. If you later want overlap-aware
   stitching, that's its own version.

## Validation

  overlap (step 200 µm, tile 200 µm). Both should produce

- On the user's 68-tile file: 68 distinct, flush, non-overlapping
