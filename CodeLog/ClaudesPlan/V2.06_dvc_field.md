## 0. The decision (two forks, presented with recommendations, chosen by the user)

The kernel (`nodegraph/kernels/aldvc_field.py`, contract in `.md`) correlates **one
ref/def volume-or-plane pair** → a dense **displacement + strain field on a COARSE
subset grid** (spacing = `subset_spacing`), *not* the full voxel grid. Two things had to
be settled before wiring; both were surfaced via one `AskUserQuestion` round with a
recommendation each.

**Fork A — how the node consumes the ref/def pair.**
- *Chosen:* a **`reference_mode` lever `{fixed_frame | previous_frame}`** + a
  `reference_frame` param, the node looping over `m,t`, **PLUS an optional `reference`
  Dataset input socket.** Leave `reference` unwired → the node **self-references** the
  same series (fixed frame `reference_frame`, or the previous frame `t−1`, per the lever).
  Wire a second loaded file into `reference` → **that external dataset is the reference**
  (at `reference_frame`, clamped m/z/c), overriding the self-reference. This is the user's
  exact phrasing: "same volume into that socket to act as same-dataset DVC, with the
  option for a second file to be loaded and be the reference frame."
  - `fixed_frame` = total displacement vs an undeformed reference (the standard
    mechanobiology result). `previous_frame` = incremental `t→t+1` fields; **`t=0` is
    skipped** (no increment into the first frame).
  - When an external `reference` is wired, the **lever governs self-reference only** —
    the external ref is always used as a fixed reference.

**Fork B — how the per-voxel displacement/strain field is represented in v2.**
- *Chosen:* **a faithful POINT structure NOW, and also a Voxel rasterizer node.** DVC
  emits a `Point` table whose points are the subset centers (`grid_coords` z,y,x, in
  **voxels** of the primary series) carrying `disp_z/disp_y/disp_x` (**µm**), a
  `disp_mag_um`, the strain-tensor components (`strain_<i><j>`, dimensionless), and the
  per-subset `qfactor` (ZNCC confidence). A separate **`transform.rasterize_field`** node
  interpolates any Point attribute column up to full-resolution Voxel layers when an
  image-space heatmap is wanted.
  - *Why POINT is the source of truth (diverges from the handoff's opening rec of Voxel
    layers):* the kernel's native output is a **coarse subset grid**; a Voxel mapping is
    not free — it fabricates per-voxel detail by interpolation (e.g. 50×50 measurements →
    512² pixels). POINT keeps the measurement at its true resolution, flows into the
    existing Point overlay + Spreadsheet + CSV/Arrow export + quiver viz, and defers the
    (lossy) interpolation to an explicit, opt-in node.

## 1. What shipped (two nodes, `nodegraph/nodes.py`)

### `analysis.dvc_field` — "DVC (ALDVC)" (category analysis)
- **Inputs:** `data` (Dataset, the deformed/moving series) + optional `reference`
  (Dataset); `channel`, `reference_frame`, `subset_size`/`subset_spacing`/`search_radius`
  (unit `px` — voxel extents set by the speckle pattern, **no** optical derive),
  `seed_levels`, `admm_iterations`, `mu`, `cc_thresh`, `strain_smooth`.
- **Modes:** `DimMode` (2D per-plane / 3D per-volume) · `reference_mode`
  {fixed_frame|previous_frame} · `correlation` {zncc|phase} · `strain_type`
  {infinitesimal|green-lagrange|almansi|hencky}.
- **Footprint:** `granularity = WHOLE_SERIES` (it crosses T to pair frames);
  `kernel_axes = {2D:{t,y,x}, 3D:{t,z,y,x}}`. **2D/3D routing reads `__modes__["dim"]`
  directly, NOT `ctx.is_volume`** (which is WHOLE_VOLUME-only and would be False under
  WHOLE_SERIES). The lever folds into the recipe hash → distinct 2D/3D memo entries.
- **Domains:** reads VOXEL, adds POINT. Output = `ds.with_structure(<Point table>)`
  (image passes through, no `meta_transform` — structure output doesn't change the image
  axes/calibration).
- **Units:** `voxel_size_um = (z_step_um, pixel_size_um, pixel_size_um)` slowest-first
  (a 2-tuple in 2D), read via `ctx.calib` (memo-fenced). Displacement voxels → µm by a
  component-wise multiply. `n_workers` is **forced to 1** (embedding-safe — kernel gotcha
  9: the ProcessPool spawn/import hazard on Windows). 3D on a single-plane series is a
  **hard error** ("z>1"; kernel gotcha 6 — a singleton-Z volume misbehaves as 3D).

### `transform.rasterize_field` — "Rasterize Field" (category transform)
- Reads POINT + VOXEL, adds VOXEL. Interpolates every non-coordinate attribute column of a
  Point layer (`source`, default `"dvc"`) onto the full voxel grid → one Voxel layer per
  column (`<source>_<column>`) via `scipy.interpolate.griddata`, nearest-filled out of
  hull (dense/finite, matching the kernel's own inpaint philosophy).
- `DimMode` lever: 2D interpolates each `(m,t,z,c)` plane from the points on that integer
  z-plane; 3D interpolates the `(z,y,x)` scatter onto the volume. **The lever (not the
  table) drives routing** — `z_kind` is NOT preserved through `with_structure` (which
  explodes a table into one AttributeLayer per column).

## 2. A latent bug fixed along the way (`graph.py`)

`analysis.dvc_field` is the **first node with two DISTINCT Dataset input sockets**
(`data` + `reference`). `nodegraph.metadata.propagate_meta` seeds a node's calibration
env from `graph.dataset_preds(nid)[0]`, but `dataset_preds` filtered `preds` in
**edge-insertion order** — so wiring `reference` before `data` (or a reference with a
different pixel size) fed the **reference's** calibration into `ctx.calib`, corrupting the
displacement→µm scale and strain rescale. Fixed: **`dataset_preds` now returns edges
ordered by declared dataset-socket position** (stable within a socket, so a `multi` socket
keeps insertion order), making `dpreds[0]` the first-declared (primary) input — matching
the engine's own socket-ordered `preds`. Only one functional caller (`propagate_meta`);
single-Dataset and `multi`-socket nodes are unaffected. Regression-guarded in the DVC
selftest (a reference with px=0.9 wired FIRST must still yield the primary's px=0.2 scale).

## 4. Addendum — cumulative accumulation + warm-start (DONE 2026-07-24)

Two follow-ups from §4's open list shipped after a grill that first settled the
underlying algorithm question ("does cumulative DVC compute differently than
incremental?").

**The algorithm finding (the thing that gated the design).** The `run_aldvc`
correlation kernel is identical for both modes; what differs is (i) *which pair* is
correlated — fixed reference vs previous frame (already the `reference_mode` lever), and
(ii) a *post-process*: incremental increments are composed into cumulative
displacement-from-reference by **Lagrangian point-tracking** (`accumulate_incremental`:
advect the reference grid points through the increments, interpolating each increment at
the points' current drifted position) with **strain recomputed** from the cumulative
displacement. This is a genuine computation — **not** a naive per-grid-point sum, and
**not** the same result as a direct `fixed_frame` correlation (small consecutive steps
stay in the correlation basin → far more robust for large total motion, which is exactly
why FranckLab does it this way). So accumulation is a legitimately **separate node**, not
a display transform. Traced through `nd2studios/pages/pipelines_page.py::_run_series_all_m`
(lines 757–818) + `nd2studios/backend/dvc/tracking.py`.

### `analysis.accumulate_field` — "Accumulate DVC Field" (category analysis)
- Reads POINT, adds POINT; footprint **WHOLE_SERIES** (crosses T to compose). Wraps the
  vendored `accumulate_incremental` + `compute_strain` (the core of
  `build_accumulated_results`; DVCResult reconstruction avoided).
- Rebuilds the ALDVC `Grid` from the increment layer's subset-center coords per
  correlation series (`(m,c)` in 3D; `(m,c,z-plane)` in 2D — `_reconstruct_grid` from the
  unique per-axis coords; `_place_on_grid` scatters each row to its cell via
  `searchsorted`, robust to row order). Increments µm→voxels, `accumulate_incremental`,
  recompute strain, voxels→µm, re-emit a cumulative Point layer (`<source>_cumulative`)
  with the **same schema** as `dvc_field` (reuses `_dvc_rows`), so it flows straight into
  the Point overlay / Spreadsheet / `rasterize_field`.
- **Metadata intelligence (user directive): inherits the config from the upstream DVC
  node's stamped provenance** — no redundant reference/dim controls. It reads
  `dvc_reference_mode` / `dvc_strain_type` / `dvc_strain_smooth` from the input Dataset
  metadata (`dvc_field` stamps these via `with_metadata`), and **dim from the generic
  `z_kind` provenance** (see §6). It **refuses** a field with no provenance (not a DVC
  field) or `fixed_frame` / external-reference provenance (already cumulative), and
  re-stamps its own output `dvc_reference_mode="cumulative"` so a second accumulate is
  refused. Pattern documented in **`wire-node-v2` §7b (provenance inheritance)**.

### Warm-start seeding on `analysis.dvc_field` (v1 parity)
- Each frame's IC-GN is now **warm-started from the previous frame's field**
  (`u0_seed`, skipping the FFT search); the first computed frame of a series always
  FFT-seeds. A new **`newFFTSearch`** bool input forces a fresh FFT seed every frame.
  Applies in **both** reference modes (mirrors v1 `_run_series_all_m`) — faithful to the
  ALDVC series workflow + more robust for motion beyond the FFT search radius. Per-z-plane
  warm-start in 2D; per-volume in 3D; reset per `m`.

**Verification:** `nodegraph.selftest` group `catalog (DVC + field rasterize)` extended —
accumulate composes a +1-voxel/frame series into cumulative `t·px` (t1=0.2 µm, t2=0.4 µm),
full schema incl. recomputed strain + qfactor, calibration fenced, and the two refusal
guards (fixed_frame / no-provenance). All 42 groups green; parity clean; GUI probe ALL
PASS. Catalog **49→50** node types.

## 6. Generic dimensionality provenance — the §7b directive applied catalog-wide (2026-07-24)

Follow-up to the user directive "update all nodes with the new metadata intelligence
directive." Rather than per-node stamping, the general form went into the **core**:

- **`Dataset.with_structure` now preserves each table's `z_kind`** (2D `plane_index` vs 3D
  `subpixel`) into a namespaced `__struct_zkind__` metadata map (keyed by domain+layer),
  read back via **`Dataset.structure_zkind(domain, layer)`**. `z_kind` was previously lost
  when a table exploded into per-column `AttributeLayer`s. **One core change ⇒ every
  structure-producing node (label / watershed / stardist / detect.spots / detect.beads /
  histogram_threshold / granule_boundary / dvc_field / accumulate_field) self-describes its
  dimensionality for free — no per-node churn.** It also folds into `output_fingerprint`
  (via `metadata`), closing a latent gap where a 2D-plane table and a 3D table with
  identical columns collided.
- **`transform.rasterize_field` lost its `DimMode` lever** and now **inherits** 2D-per-plane
  vs 3D-volumetric routing from the source field's `z_kind`. This fixes a real *default*
  silent-corruption bug: on a `z>1` image the lever defaulted to 3D, so a 2D per-plane DVC
  field (whose `z` is a stored plane index, not a coordinate) was misread as a 3D grid.
  Fixed footprint `WHOLE_VOLUME` + `kernel_axes={z,y,x}` (a superset; the compute loops
  units internally). `analysis.accumulate_field` inherits dim the same way (its earlier
  DVC-specific `dvc_dim` stamp was dropped in favour of the generic `z_kind`).
- **Clobber guard:** `analysis.measure` re-emits its LABEL layer, so it now carries the
  upstream label's `z_kind` forward (`ds.structure_zkind(...) or "subpixel"`) instead of
  overwriting it with the `StructureTable` default.
- Verified: new selftest coverage — `dataset` group (`z_kind` provenance, COW-safe, two
  layers keep independent kinds), the label→measure `z_kind`-preservation guard, and a
  rasterize §7b regression (a 2D field on a `z>1` image is NOT bled across z). All **42
  groups** green; parity clean; GUI probe ALL PASS. Documented in **`wire-node-v2` §7b**
  (generic `z_kind` case + the general stamp-and-inherit pattern).
