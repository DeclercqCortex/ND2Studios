# V1.30 — Preserve Z stacks through the stitched-TIFF exporter

## Bug

When the user opens the Stitch dialog with a multi-Z ND2 and picks
`Z mode = none` (expecting all Z slices to be preserved in the stitched
output), the resulting TIFF still collapses to a single Z plane.

Root cause in `nd2studios/backend/exporters/stitch_exporter.py`:

```python
all_frames = np.zeros(
    (n_t, 1, n_c, layout.canvas_h, layout.canvas_w), dtype=volume.dtype
)
for t in range(n_t):
    for c_idx, c in enumerate(channel_indices):
        ...
        f = volume.get_frame(c=c, m=m, t=t, z=z_index, z_mode=z_mode)
        ...
        all_frames[t, 0, c_idx] = stitch_one_frame(tiles, layout, ...)
```

The output array is always `Z=1` and the loop reads the single Z slice
named by `z_index`. There is no iteration over Z.

In the rest of the app `LazyND2Volume.get_frame(z_mode="none", z=...)`
returns the single (H, W) frame at the requested Z (see
`nd2_volume.py:155`). So with `z_mode="none"` the stitch path was
behaving as "pin to a single Z slice" — which contradicts the dialog
labelling "Z mode: none" as "keep all Z".

## Goal

When `z_mode == "none"` and `n_zslices > 1`, the stitched TIFF must
contain every Z plane: shape `(T, Z, C, H, W)`. Projection modes
(`max`, `mean`, `min`) and `z_mode == "none"` with single-Z files
continue to produce `(T, 1, C, H, W)`. File construction stays an
ImageJ TZCYX hyperstack with `Labels`, `unit=um`, `spacing`, resolution.

## Approach

1. **Stitch exporter** — in `export_stitched_tiff`:
   - Compute `preserve_z = (z_mode == "none" and volume.n_zslices > 1)`
     and `n_z_out = volume.n_zslices if preserve_z else 1`.
   - Allocate `(n_t, n_z_out, n_c, canvas_h, canvas_w)`.
   - Recompute the BigTIFF threshold including `n_z_out`.
   - Inside the `(t, c)` loop, add an inner Z loop:
     `for z_out in range(n_z_out)` with `z_request = z_out if preserve_z
     else z_index`. Stitch tiles into `all_frames[t, z_out, c_idx]`.

2. **Stitch dialog** — update the "Z slice (when 'none')" spinbox so it
   no longer misleads users:
   - Hide / disable it when `z_mode == "none"`. It only made sense
     under the old single-slice semantics.
   - When `n_zslices == 1`, hide it regardless.
   - Wire `combo_z.currentTextChanged` to:
     - Update spinbox enabled state.
     - Refresh the size estimate in `_refresh_summary` (file gets
       `n_z` times bigger when Z is preserved).

3. **Z_index pass-through** — `StitchRequest.z_index` and `combo_z`
   already plumb through to `export_stitched_tiff`. No data-flow
   change beyond the exporter.

## Files modified

- `nd2studios/backend/exporters/stitch_exporter.py` — Z-aware allocation + loop
- `nd2studios/pages/stitch_dialog.py` — UI cleanup, size estimate update
- `CodeLog/Updates/CHANGELOG.md` — Bug Fixes entry
- `CodeLog/Architecture/ARCHITECTURE.md` — exporter signature note

## What stays the same

- Tile layout (`compute_tile_layout`), serpentine fallback, single-frame
  stitching (`stitch_one_frame`), and the ImageJ metadata fields written
  by `tifffile.imwrite` are untouched. Only the Z axis is allowed to
  grow past 1.

## Loader follow-up (same V1.30 fix)

The exporter half alone wasn't enough: the **loader** silently collapsed
Z back to 1 on re-import. Three issues in the TIFF load path:

1. `load_imagej_tiff_channels` built `LazyTIFFChannel(n_pages_per_t=n_z*n_c,
   page_within_t=c_idx)` but never passed `n_z`, so each per-channel
   proxy read only the `z=0` page for every T. Even worse, the existing
   multi-Z code in `LazyTIFFChannel._read_frame` used `base_page + z`
   (stride 1), which is wrong for TZCYX layout where Z stride within a
   channel = `n_c`.
2. `LoadWorker._load_tiff` hardcoded `n_zslices=1` in the returned
   metadata and returned `volume=None`, so the Import page's
   multi-axis viewer never got a Z scrollbar for a single TIFF file.
3. `_SingleFileTIFFView.get_frame` ignored its `z` parameter entirely
   and `to_lazy_channel` ignored `z_mode`/`z_index`. So even a
   correctly-built volume wouldn't let the viewer scroll Z.

Fixes (in addition to the exporter changes above):

- **`LazyTIFFChannel`** gains a `z_stride: int = 1` parameter; the Z
  read loop uses `base_page + z * z_stride`. Single-channel multi-Z
  files keep `z_stride=1` (default); multi-channel ImageJ files set
  `z_stride=n_c`.
- **`load_imagej_tiff_channels`** now passes `n_z=n_z, z_stride=n_c,
  z_projection=<param>` (default `"max"`) so per-channel proxies are
  Z-aware. New `z_projection` keyword argument.
- **`_SingleFileTIFFView`**:
  - Caches an internal `tifffile.TiffFile` handle (`_ensure_tiff`)
    closed in `close()`.
  - `get_frame` adds a multi-Z branch (`self.n_zslices > 1`) that
    reads the page directly via `page = t*n_z*n_c + z*n_c + c` and
    honors `z_mode` (`none` pins to `z`; `max`/`mean`/`min` reduce
    across `[z_start, z_end)`).
  - `to_lazy_channel` builds a fresh `LazyTIFFChannel` whose
    `page_within_t`/`n_z`/`z_stride` reflect the requested
    `z_mode`/`z_index`. Falls back to the cached single-Z proxy when
    `n_zslices <= 1`.
- **`LazyMultiFileTIFFVolume.to_lazy_channel`** now passes
  `z_mode`/`z_index`/`z_start`/`z_end`/`t_*` through to the underlying
  `_SingleFileTIFFView.to_lazy_channel` for chain `C`/`M`/`Z` (was
  silently dropping all of them).
- **`LoadWorker._load_tiff`** now always builds a
  `LazyMultiFileTIFFVolume([self.filepath], chain_axis="Z")` and pulls
  per-channel lazy proxies + metadata from it. Single-channel
  single-Z files still produce the same shape; multi-Z and multi-channel
  files now correctly report `n_zslices`, `n_channels`,
  `n_timepoints` and expose `volume` so the multi-axis viewer can
  scroll Z.

End result: a stitched TIFF written with `z_mode="none"` reopens with
its full Z stack intact, scrollable in the Import viewer exactly like
the source ND2.

## Reload compatibility note

`tiff_loader.read_imagej_tiff_metadata` already understood `(T, Z, C,
H, W)` TZCYX. The bug was downstream of that — in the channel-builder
and volume-routing code. After this V1.30 patch, the load path can
faithfully serve multi-Z multi-channel TIFFs end to end.
